# ADR-0006: 근거 답변의 거절 판단과 출처 표기

- 상태: 채택 (2026-10-12), 보완 (2026-10-14 — 결정 1 실측 결과, 결정 4 추가)
- 이슈: #19
- 결정한 사람: 소유자(miin-jun)
- 관련: [ADR-0002 리랭커](0002-reranker.md) "후속"의 거절 로직 경고, [ADR-0005 `search_documents` 계약](0005-search-documents-contract.md),
  형식 [data-design.md](../data-design.md) 2절 "출처 표기 규칙"·5절 반환 표, 측정 코드 `eval/reranker_score_dist.py`

#19는 검색 결과로 답변을 만들면서 ① 근거가 없으면 거절하고 ② 답변에 출처를 단다. 구현 전에 거절을 무엇으로
판단할지, 출처를 청크 종류별로 어떻게 적을지, 개발에 쓸 모델을 정한다.

## 결정 1: 거절은 LLM이 청크 내용을 보고 판단한다

리랭커 점수 임계값으로 거절하지 않는다. 검색 결과(청크)를 LLM에 넘기고, LLM이 질문이 묻는 사실이 청크에
있는지 보고 답하거나 "문서에서 찾을 수 없음"으로 거절한다.

### 근거 (2026-10-12 실측)

조건: 별칭 `rfp_chunks` → `rfp_chunks_v2_kure`(3,499건), TEI 1.9.4 `nlpai-lab/KURE-v1`·`BAAI/bge-reranker-v2-m3`,
qa_v2 57문항을 서비스 경로 `search_documents(top_k=10)`(하이브리드 + 리랭크 N=20)로 검색. 57문항 모두 10건 반환.
정답 청크는 `gold_chunk_ids`의 `block_requirement` 기준이다.

- A: 답 있음 + 모든 evidence의 정답 청크가 상위 10 안
- B: 답 있음 + 정답 청크가 상위 10에 다 들어오지 못함(2문항은 일부만 들어옴)
- C: 답 없음

리랭커 1위 점수 분포:

| 그룹 | 문항 | 최소 | 25% | 중앙값 | 75% | 최대 |
|---|---|---|---|---|---|---|
| A | 33 | 0.002 | 0.281 | 0.713 | 0.918 | 0.999 |
| B | 18 | 0.002 | 0.071 | 0.395 | 0.815 | 0.992 |
| C | 6 | 0.036 | 0.178 | 0.561 | 0.761 | 0.855 |

"1위 점수 < t 이면 거절"로 했을 때:

| t | A 잘못 거절 | B 거절 | C 통과(거절 못 함) |
|---|---|---|---|
| 0.05 | 4/33 | 3/18 | 5/6 |
| 0.1 | 6/33 | 6/18 | 4/6 |
| 0.2 | 7/33 | 7/18 | 4/6 |
| 0.3 | 9/33 | 7/18 | 4/6 |
| 0.5 | 15/33 | 11/18 | 3/6 |
| 0.7 | 16/33 | 12/18 | 2/6 |
| 0.8 | 19/33 | 13/18 | 1/6 |
| 0.9 | 24/33 | 15/18 | 0/6 |

- A와 C를 완전히 가르는 임계값이 없다. C 6문항이 모두 A의 범위 안에 있고, A 33문항 중 20문항이 C의 최고점(0.855) 이하다
- C를 전부 거절하려면 t = 0.9가 필요하고, 그때 A 24/33을 잘못 거절한다
- A에서 정답 청크가 1위인 문항(21/33)만 봐도 1위 점수 최소가 0.016이고 11문항이 0.855 이하다. 정답을 1위로 찾은 경우도 C와 겹친다
- 1위와 2위의 점수 차도 A(0.001~0.831)와 C(0.009~0.706)의 범위가 같다
- A에서 1위 점수가 0.3 미만인 9문항 중 6문항이 `paraphrase` 태그다
- 결과: `data/eval/results/answer/reranker_score_dist_20261012.jsonl`.
  다시 재려면 `uv run python -m rfp_pm_agent.eval.reranker_score_dist --out <경로>`
- 재현성: 같은 조건으로 다시 실행했을 때 그룹(A·B·C)·정답 청크 순위·1위 청크·임계값 표는 57문항 모두 같았다.
  리랭커 점수는 호출마다 최대 0.0015 달랐고(같은 질의를 3회 반복해도 달라지는 문항이 있었다), 점수 차가 그보다 작은
  두 청크의 순서가 2문항(q013 3·4위, q017 7·8위)에서 바뀌었다. 점수가 달라지는 원인은 확인하지 않았다

### 관찰 (검증하지 않음)

C에서 점수가 높은 4문항(q045 0.855, q034 0.783, q056 0.695, q032 0.426)은 1위 청크가 모두 질문에 적힌 사업명을
담은 사업 개요·사업명 청크였다. 질문이 묻는 사실(충전기 수, 지원 외국어 등)이 없어도 사업명이 맞는 청크에 높은
점수가 붙은 것으로 보인다. 1위 청크 앞 50자만 보고 한 해석이다.

→ 프롬프트는 "질문이 묻는 사실이 청크에 있을 때만 답한다"로 쓴다. 사업명·주제가 맞는 것만으로는 답하지 않는다.

### 버린 대안

- **점수 임계값만으로 거절** — 위 표대로 A와 C가 겹친다
- **점수 임계값 + LLM 병행**(점수가 낮으면 LLM을 부르지 않고 거절) — 가장 낮은 후보 0.05에서도 A 4/33을
  LLM에 보내기 전에 잃고, C는 1문항만 걸러진다. 얻는 것(LLM 호출 절약)보다 잃는 정답이 크다

검색 결과가 0건일 때 LLM을 부르지 않고 바로 거절할지는 점수 판단과 별개라 #19 구현에서 정한다.

→ 2026-10-14 결정: 검색 결과가 0건이면 LLM을 부르지 않고 거절한다(비용 0). 넘길 청크가 없어 LLM이 볼 근거가 없다
(data-design.md 5절 "근거 답변 `answer_question`").

## 결정 2: 출처 표기 5가지

`DocumentHit`의 `format`·`requirement_id`·`printed_page`·`page`로 정한다. 문서명은 `bid_title`이다.

| 청크 종류 | 조건 | 표기 | 색인 청크 수 |
|---|---|---|---|
| PDF 요구사항(인쇄 쪽 있음) | `format=pdf`, `requirement_id` 있음, `printed_page` 있음 | `[문서명 p.23 · SFR-001]` | 107 |
| PDF 요구사항(인쇄 쪽 없음) | `format=pdf`, `requirement_id` 있음, `printed_page` null | `[문서명 PDF 15쪽 · SFR-001]` | 21 |
| PDF 블록 | `format=pdf`, `requirement_id` null | `[문서명 PDF 15쪽]` | 2,341 |
| HWP 요구사항 | `format=hwp`·`hwpx`, `requirement_id` 있음 | `[문서명 · SFR-001]` | 294 |
| HWP 블록 | `format=hwp`·`hwpx`, `requirement_id` null | `[문서명]` | 736 |

- `p.23`은 `printed_page`(페이지 하단에서 읽은 인쇄 쪽번호) 그대로다
- `PDF n쪽`의 n은 `page + 1`이다. `page`는 0부터 세는 PDF 페이지라, 1을 더하면 PDF 뷰어에 보이는 쪽번호가 된다.
  "PDF"를 붙여 인쇄 쪽번호와 구별한다
- 인쇄 쪽번호를 계산해서 만들지 않는다. `printed_page`가 null이면 `PDF n쪽`으로 적는다
  (data-design.md 2절 원칙: 고정 오프셋으로 쪽번호를 추정하지 않는다)

### 근거

- 청크 수는 색인된 `data/chunks/block_requirement.jsonl` 3,499건을 `data/parsed/`와 묶어 센 값이다(2026-10-12, 문서 HWP 7건·PDF 3건).
  합계 107 + 21 + 2,341 + 294 + 736 = 3,499
- 기존 규칙(data-design.md 2절)의 예시 `[문서명 p.23(인쇄) · SFR-001]`에 그대로 맞는 청크는 107건(3%)뿐이었다.
  요구사항 ID가 없는 블록 청크 3,077건(88%)은 표기가 정해져 있지 않았고, 인쇄 쪽번호가 없을 때 붙일 "안내 문구"도 문장이 없었다
- HWP·HWPX는 페이지 개념이 없다(Silver에 `pdf_page`가 없다). 섹션 경로(`heading_path`)는 #11에서 폐기해 인덱스에 없다

### 버린 대안

- **인쇄 쪽번호 추정 계산**(`page`에 고정 값을 더하거나 빼서 `p.n`으로 표기) — 표지·목차 때문에 문서마다 차이가 다르다.
  천안시 PDF에서 `printed_page == page`였던 것은 우연이었다(data-design.md 2절). 틀린 쪽번호는 없는 것보다 나쁘다
- **`p.23(인쇄)`처럼 "(인쇄)"를 붙이는 표기** — 인쇄 쪽이 아닌 경우에 "PDF"를 붙여 구별하므로 뺐다

## 결정 3: 개발 모델은 GPT-6 Luna

- API 모델 ID `gpt-6-luna`(날짜 붙은 스냅샷 없음). `.env`의 `LLM_MODEL_DEV`에 넣는다
- 가격(OpenAI 공식 가격표·모델 페이지, 2026-10-12 확인): 입력 $0.10 / 출력 $0.50 per 1M 토큰(캐시된 입력 $0.01).
  `LLM_PRICE_INPUT_PER_1M=0.10`, `LLM_PRICE_OUTPUT_PER_1M=0.50`.
  입력이 272K 토큰을 넘는 요청은 입력 $0.20 / 출력 $0.75다 — #19는 청크 10~20개라 해당하지 않는다
- 추론 강도는 `low`로 호출한다(`LLM_REASONING_EFFORT`, 기본 `low`)
- 최종 평가 모델(`LLM_MODEL_EVAL`)은 #25에서 정한다

### 근거

- 설계 원칙이 "개발 중은 가장 싼 모델"이다(tech-stack.md 5절, CLAUDE.md 비용). 같은 날 공식 가격표에서
  `gpt-5.6-luna`는 입력 $0.20 / 출력 $1.20, `gpt-6-luna`는 입력 $0.10 / 출력 $0.50이었다
- 처음에는 `gpt-5.6-luna`로 정했다가(2026-10-12), 모델 목록에서 더 싼 `gpt-6-luna`를 확인하고 같은 날 바꿨다.
  두 모델의 답변 품질은 비교하지 않았다 — 가격만으로 골랐다

### 주의 (2026-10-12 공식 문서 확인)

- 이 모델은 추론(reasoning) 토큰을 쓴다. 추론 강도는 `none`·`low`·`medium`·`high`·`xhigh`·`max`를 받고 기본값은 `medium`이다
- 추론 토큰은 응답에 보이지 않지만 출력 토큰으로 과금된다. 답변이 짧아도 출력 토큰 수가 답변 길이보다 클 수 있다
- 추론 강도는 Chat Completions의 `reasoning_effort` 인자로 정한다. `clients/llm.py`가 `LLM_REASONING_EFFORT` 값을 보낸다
- 모델 페이지에 따르면 Chat Completions에서 함수 호출(function calling)은 추론 강도가 `none`일 때만 된다.
  #19는 함수 호출을 쓰지 않아 영향이 없지만, #22(에이전트)는 Responses API를 쓰거나 `none`으로 불러야 한다 — #22에서 정한다
- 출처: <https://developers.openai.com/api/docs/pricing>, <https://developers.openai.com/api/docs/models/gpt-6-luna>,
  <https://developers.openai.com/api/docs/guides/reasoning>

## 결정 4: 근거 답변은 문서 지정(`doc_ids`)을 전제로 쓴다 (2026-10-14)

`answer_question`은 대상 문서를 `doc_ids`로 받아 검색을 그 문서로 좁힌 상태로 쓴다. 전체 검색(`doc_ids=None`)은
막지 않지만, 통과 기준을 만족한 조건은 문서 지정뿐이다.

### 근거

- 결정 1 "실측 결과" 표 — 바뀐 변수가 `doc_ids` 하나인 두 실행에서 잘못 거절이 11/33(미통과)에서 1/40(통과)으로 줄었다.
  답 없음·무관 질문 거절은 두 조건 모두 통과했다
- 전체 검색에서는 사업명 없는 질문이 두 가지로 실패한다. 어느 사업인지 정할 수 없어 거절하거나(8개),
  다른 사업의 답이 출처와 함께 나온다(q010). 뒤쪽은 출처 형식이 맞아 DoD ①이 잡지 못한다(#25 Citation 정확도 채점 대상)
- qa_v2 질문은 특정 문서를 보고 있다는 전제("이 사업")로 만들었고, 실제 사용도 RFP 하나를 열어 두고 묻는 방식이다

### #22(에이전트)에 넘기는 요구사항

- 질문에 대상 문서가 없으면 사용자에게 어느 사업인지 묻거나, 대화 맥락에서 `doc_ids`를 정해 `answer_question`에 넘긴다
- 무관 질문(대상 문서가 없는 질문)은 이번 측정에서 전체 검색으로 5/5 거절했다. 에이전트가 문서를 정하지 못한 질문을 어떻게 다룰지는 #22에서 정한다
- → 2026-10-16 #22: 에이전트 검색은 `doc_ids` 필수, 사업 목록을 system 프롬프트에 두고 정하지 못하면 되묻는다([ADR-0010](0010-langgraph-agent.md) 결정 3)

### 버린 대안

- **전체 검색 그대로 프롬프트만 고치기** — 문서가 섞인 검색 결과에서 사업을 정하는 일을 LLM에 맡기게 된다. q010처럼 틀린 사업을 고르면
  출처까지 달린 오답이 나온다. 프롬프트 v2는 측정하지 않았다(한 번에 하나만 바꾼다)

- 답 없음 6문항은 모두 실제 사업을 묻는 질문이다. 사업과 무관한 질문(예: 날씨)의 리랭커 점수는 재지 않았다
- (2026-10-12 작성) LLM이 거절을 얼마나 정확히 하는지는 아직 재지 않았다. 이 결정은 "점수로는 안 된다"까지만 측정으로 뒷받침된다
  → 2026-10-14 #19 실행에서 쟀다(결정 1 "실측 결과"). 그 측정의 한계는 아래와 같다
- 각 조건을 1회만 실행했다. 같은 입력에서도 LLM 출력이 달라질 수 있다 — B 그룹 q051은 전체 검색에서 답했고, 문서 지정에서는
  같은 청크(b0015)가 검색 1위였는데 거절했다
- q037(표 범위 해석)·q027(표현 차이)이 전체 검색에서 거절되고 문서 지정에서 답한 원인은 확인하지 않았다. 다른 문서의 청크가 섞인 것이 원인일
  수 있다는 것은 추정이다
- 문서 지정 조건의 입력 토큰이 전체 검색보다 37% 많았다(252,957 → 346,777). 한 문서 안에서 긴 청크가 상위에 더 많이 올라온 것으로
  보이지만 청크별로 확인하지 않은 추정이다
- qa_v2의 정답 청크 목록(`gold_chunk_ids`)이 빠뜨린 청크가 있는 것으로 보인다. q013은 정답 청크가 아닌 b0022를 인용해 맞게 답했고
  b0022에도 같은 금액이 적혀 있다. q007이 인용한 b0048·b0007도 정답의 평가 비율을 담고 있다. 평가 세트는 고치지 않았다 — #25 채점에서 고려한다
- HWP 블록 청크 736건(21%)은 출처가 문서명뿐이다. 문서 안 어디인지 가리키지 못한다 — 파서가 HWP에서 위치 정보를 얻지 못하는 한계다
- PDF 블록 청크 2,341건(67%)은 인쇄 쪽번호가 없어(Silver `Block`에 없다) 항상 `PDF n쪽`으로 표기된다
