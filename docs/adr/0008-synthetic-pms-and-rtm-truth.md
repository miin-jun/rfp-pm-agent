# ADR-0008: 합성 PMS 데이터와 RTM 정답을 생성 시점에 함께 기록

- 상태: 채택 (2026-10-15, PR #90)
- 이슈: #20 (정답을 쓰는 곳: #21 조회 툴, #25 평가, #39 RTM)
- 결정한 사람: 소유자(miin-jun). 스키마는 기존 설계(data-design.md 6절), 생성 방식·v2 수정 방향은 소유자 지시, 누락 후보 규칙(사업관리 제외)은 Claude가 해석하고 소유자가 승인, 구현·측정은 Claude
- 관련: [data-design.md](../data-design.md) 6절(스키마·판단 규칙)·7절(합성 생성 규칙), [tech-stack.md](../tech-stack.md) 7절(PostgreSQL),
  코드 `pms/models.py`·`pms/rules.py`·`pms/draft.py`·`pms/synth.py`·`pms/load.py`, 마이그레이션 `migrations/versions/`

## 맥락

- 이 레포의 질문("이번 주 지연 업무", "미해결 Risk", "요구사항 누락")에 답하려면 프로젝트 관리 데이터가 있어야 하는데, 실제 PMS 데이터는 없다
- 평가하려면 정답이 필요하다. 데이터를 먼저 만들고 정답을 사람이 따로 붙이면 비용이 크고, 데이터와 정답이 어긋날 수 있다
- 그래서 data-design.md 7절은 "정답을 알고 만든다"를 원칙으로 정했다. 이 ADR은 그 원칙을 어떻게 구현했는지, v1 정답에서 무엇이 틀렸고 어떻게 고쳤는지를 기록한다

## 결정

### 1. DB는 compose의 PostgreSQL 16, 스키마는 data-design.md 6절 10개 테이블

`projects`, `users`, `project_members`, `requirements`, `wbs_items`, `wbs_requirements`, `deliverables`, `risks`, `issues`, `documents`.
SQLAlchemy 2 모델 + Alembic 마이그레이션(`uv run alembic upgrade head`).

- WBS 번호는 프로젝트 안에서만 유일하므로 업무 참조는 `(project_id, wbs_id)` 복합 FK다. 담당자(`project_members`)와 Issue의 Risk 참조도
  `(project_id, …)` 복합 FK로 걸어 다른 프로젝트의 행을 가리키지 못하게 한다
- 상태 값, 확률·영향(1~5), 진척률, `planned_start ≤ planned_end`, done ⇔ (진척 100, actual_end 있음), 제출일 ⇔ 제출 상태, 해결일 ⇔ resolved는
  CHECK 제약으로도 막는다. 생성 코드의 검증(`validate`)을 거치지 않은 행도 DB가 거부한다
- 에이전트용 `agent_ro` 계정은 SELECT만 된다(CREATE TABLE은 permission denied)

### 2. RTM 정답은 `wbs_requirements` + `data/eval/pms_truth_v2.json`

- **#39 누락 채점은 일부러 뺀 누락 후보(`reason: "injected"`)만 쓴다(소유자 결정, 2026-10-15).** LLM이 연결을 빠뜨린 `llm_omitted`는 정답이 아니다 —
  v1 3건·v2 2건 모두 검수에서 진짜 누락이 아니었다. 파일에는 기록으로 남기고 항목마다 `use_for_scoring`(injected만 true)을, 파일 머리에 `scoring` 설명을 둔다

- 요구사항 ↔ 업무 연결은 `wbs_requirements`가 그대로 정답이다. 요구사항 → 업무 → 산출물 경로, 누락 후보, 범위 외 후보, 지연·미해결 Risk·미제출 산출물은
  정답 파일에 둔다
- 정답 파일의 판단(지연, 이번 주 지연, 미해결 Risk)은 주입 목록이 아니라 `pms/rules.py`(data-design.md 6절 정의)로 최종 데이터에서 계산한다.
  조회 툴(#21)의 SQL도 같은 정의를 따른다. 적재 후 `agent_ro`로 6절 정의를 SQL로 옮겨 센 값이 정답 파일 수치와 같은지 확인했다

### 3. LLM은 WBS 초안만 만들고, 판단이 들어가는 값은 코드가 seed로 정한다

- 원천: 실제 RFP 9건(색인 청크 파일에 요구사항 청크가 모두 있고 요구사항 20건 이상), 요구사항 416건. 요구사항은 `source_chunk_id`로 검색 청크와 이어진다
- LLM(프로젝트당 1회): 업무 이름·단계·연결 요구사항·산출물 이름. 프롬프트 `pms/prompts/wbs_draft_v2.md`
- 코드(seed = `SYNTH_SEED` + doc_id): 프로젝트·단계·업무 날짜, 기준일 기준 상태, 지연 주입(말단 업무 15%, 프로젝트마다 이번 주 지연 1건 이상),
  담당자, 산출물 마감·제출, Risk·Issue(5~10개, open 2개 이상)

### 4. 누락 후보는 사업관리 계열을 뺀 요구사항에서만 고른다

프로젝트마다 요구사항 전체의 12%(최소 1건)를 **PMR(프로젝트관리)·PSR(지원)을 뺀** 요구사항에서 seed로 골라 LLM에 주지 않는다.
관리 업무(착수·주간·완료보고, 사업수행계획)는 어느 사업에나 있어서, 관리 요구사항을 빼도 비슷한 업무가 생겨 "대응 업무가 없다"는 정답이 틀리게 된다.
v1에서는 일부러 뺀 50건 중 12건(PMR 7, PSR 5)이 관리 요구사항이었다.

- **소유자 승인 (2026-10-15)**: 소유자 지시는 "기능 요구사항에서만"이었다. Claude가 아래 이유로 "사업관리 제외"로 해석해 구현했고, 소유자가 이 해석을 승인했다.
  검토했던 다른 방법은 "SFR을 먼저 고르고 모자라면 사업관리를 뺀 나머지에서 채우기"다
- "기능 요구사항에서만"을 SFR(기능)만으로 해석하지 않았다. PRJ-01은 3건이 필요한데 SFR이 1건, PRJ-06은 9건이 필요한데 SFR이 7건이라 채울 수 없다.
  그래서 사업관리를 뺀 시스템 요구사항 전체(기능·성능·데이터·보안·품질·인터페이스·시험 등)를 후보로 한다. v2의 50건 구성: SFR 12, SER 8, QUR 6, TER 5,
  COR 4, DAR 4, PER 4, ECR 3, SIR 2, INR 1, CUR 1

### 5. 기준일은 2026-09-24(목)

기존 예시 `AS_OF_DATE=2026-09-21`은 월요일이라 "이번 주 지연"(이번 주 월요일 ~ 기준일 전날) 구간이 비어 #21 `scope="this_week"`를 시험할 수 없다.
정의는 그대로 두고 값만 바꿨다. `generate`는 기존 정답 파일의, `load`·`stats`는 데이터 파일의 기준일이 `AS_OF_DATE`와 다르면 멈춘다
(실제로 `.env`가 09-21이던 동안 멈춰서 불일치를 찾았다).

### 6. LLM 초안은 git에 보관한다

`data/synth/wbs_drafts/<프롬프트 버전>/<doc_id>.json`(9개, 약 110KB, `.gitignore` 예외). 정답 파일만 git에 있고 입력이 없으면, 초안을 잃었을 때 LLM을 다시
불러야 하고 결과가 달라져 정답과 같은 DB를 다시 만들 수 없다. 내용은 LLM이 만든 업무명·요구사항 ID·산출물 이름뿐이다(RFP 원문 없음).
정답 파일에 프로젝트별 초안 sha256을 남긴다. 생성 결과 `data/synth/pms_v2.json`은 초안 + seed로 다시 만들 수 있어 올리지 않는다.
v1 정답(`pms_truth_v1.json`)과 v1 초안(`wbs_draft_v1/`)은 오류 기록으로 보존한다. 단, v1 정답은 **커밋 `f0cf772`의 코드로만** 다시 만들 수 있다 —
지금 코드는 누락 후보 규칙(사업관리 제외)·초안 프롬프트 버전(v2)·이번 주 지연 후보(④ 추가)가 달라 v1 초안을 쓰지 않는다.

## 버린 대안

- **별도 `rtm_gold(req_id, task_id, deliverable_id)` 테이블**: `wbs_requirements`와 같은 내용을 두 곳에 두게 된다. 하나만 고치면 둘이 어긋나고,
  에이전트가 읽는 DB에 정답 테이블이 있으면 툴이 정답을 그대로 읽을 수 있다. 정답은 DB 밖(`data/eval/`)에 두고 평가 코드만 읽는다
- **SQLite**: 설정 없이 쓸 수 있지만, 기술 스택이 PostgreSQL 16으로 확정돼 있고(tech-stack.md 7절) compose에 이미 있다. 읽기 전용 계정(`agent_ro`)
  같은 권한 분리, `ARRAY` 열(`documents.allowed_roles`)을 SQLite로는 같은 방식으로 시험할 수 없다

## v1 정답의 오류와 v2 수정

### 발견: 검수 3건

소유자가 v1 정답의 `llm_omitted`(LLM이 받은 요구사항을 어느 업무에도 연결하지 않은 것) 3건을 요구사항 원문과 함께 보여 달라고 요청했고,
Claude가 원문과 WBS 업무 목록을 대조해 판정했다. 소유자는 이 결과를 보고 v2로 고치기로 정했다.

| 프로젝트 | 요구사항 | 내용 | 비슷한 업무(연결 없음) |
|---|---|---|---|
| PRJ-02 | PMR-008 보고 관리 | 주/월간 보고, 회의록, 비정기 보고회 | `1.2 착수보고`, `5.5 주간보고 및 진행관리`, `5.7 완료보고 및 사업 종료` |
| PRJ-03 | PMR-002 프로젝트 일정계획 | 사업수행계획서·착수보고서·주/월간보고서·완료보고서 | `1.1 착수 및 사업수행계획 수립`, `5.7 사업 완료 및 산출물 인계` |
| PRJ-06 | PMR-008 의사소통 관리 | 주간·월간 정기보고, 착수·중간·완료보고, 이슈 보고 | `1.2 착수보고`, `1.7 주간보고 및 이슈관리` |

3건 모두 대응하는 업무가 있었다. 이 업무들은 "범위 외 후보"(요구사항 없는 업무)로도 잘못 들어가 있었다 — 정답이 두 군데서 틀렸다.

### 원인: 초안 프롬프트 v1 규칙 5

> 5. 착수보고·주간보고·완료보고 같은 사업관리 업무 2~4개는 requirement_ids를 빈 목록으로 둔다.

RFP에는 바로 그 보고 업무를 요구하는 PMR 요구사항이 있다. LLM은 규칙대로 보고 업무를 비워 두었고, 보고 요구사항은 연결될 업무가 없어 `llm_omitted`가 됐다.

### 자동 검증이 못 잡은 이유

- `validate`는 구조(키·참조·날짜 순서·상태와 날짜)를 본다. "연결이 없다"는 사실은 맞았고, "연결이 없지만 내용상 대응하는 업무가 있다"는 요구사항 원문과 업무 이름의
  뜻을 비교해야 알 수 있다
- 단위 테스트는 정해 둔 가짜 초안을 쓰므로 프롬프트 문구가 만드는 LLM 행동을 시험하지 못한다
- 통계(RTM 커버리지 87.3%, LLM에 준 것 기준 363/366)는 정상 범위로 보였다. 틀린 3건이 수치에 작게 섞여 있었다

### v2로 해결

- 프롬프트 v2 규칙 5: "보고·일정 등 사업관리 요구사항(PMR 등)이 목록에 있으면 해당 관리 업무에 연결한다. 연결할 요구사항이 없는 관리 업무만 빈 목록으로 둔다"
- 누락 후보는 사업관리 계열을 뺀 요구사항에서만 고른다(결정 4)
- v2에서 같은 방식으로 검수한 결과는 아래 "결과"

**10건 중 5건은 비슷한 업무가 있고, 2건은 일부만 겹치며, 3건만 비슷한 업무가 없다.** LLM은 빠진 요구사항을 모르지만, 성능 검증·인증 구현 같은 일반 업무를 만들면서
빠진 요구사항의 내용도 덮는다. 그래서 이 정답의 뜻은 "`wbs_requirements` 연결이 없다"이고 "비슷한 업무가 없다"가 아니다. 이 차이를 #39 채점에서 어떻게 다룰지는 #39로 미뤘다(재검토).

## 한계

- **실제 PMS 분포와 다를 수 있다**: 지연 15%, Risk·Issue 5~10개, 단계 비율(15·20·35·20·10%), 업무 기간은 정해 둔 값과 균등 난수다.
  실제 사업의 지연 분포(특정 단계에 몰림, 연쇄 지연), Risk 확률·영향 분포와 다르다. 이 데이터로 잰 툴·에이전트 성능은 실제 PMS에서 다를 수 있다
- **정답 검수는 표본만**: 원문 대조는 `llm_omitted` 전부(v1 3건, v2 2건)와 일부러 뺀 누락 후보 10건(50건 중)만 했다. 대조와 판정은 Claude가 했고,
  **소유자가 확인한 것은 `llm_omitted` 5건(v1 3건, v2 2건)뿐**이다. 무작위 10건은 Claude 판정이며 소유자 검수가 아니다. 채점에 쓰는 injected 50건은 사람이 내용을 검수하지 않았다
  (생성 과정에서 "연결 없음"은 보장되지만 "비슷한 업무 없음"은 보장되지 않는다). 지연·Risk·산출물 정답은 규칙으로 계산했고
  SQL 집계로 맞춰 봤지만, 업무 이름과 요구사항 연결(LLM 초안)이 내용상 맞는지는 표본 외에는 보지 않았다
- **누락 정답의 뜻**: 위 검수처럼 일부러 뺀 요구사항의 절반은 비슷한 업무가 있다(10건 중 5건)
- **범위 외 후보가 v2에 없다**: v2 규칙 5로 관리 업무가 모두 PMR에 연결돼 요구사항 없는 업무가 0건이다. v1 결정("PRJ-07·09는 범위 외 후보 0건이어도 유지")은
  v2에서 9개 프로젝트 전체로 넓어졌다. #39의 "범위 외 후보" 검출은 이 데이터로 시험할 수 없다
- **파싱 결과의 빈 요구사항**: PRJ-06 PSR-003처럼 내용이 빈 요구사항이 1건 있다. 요구사항 테이블에 그대로 들어가 있다
- **번호 의존**: 프로젝트·사용자 번호는 원천 문서 doc_id 순서로 매긴다. 조건을 만족하는 문서가 늘면 번호가 밀린다. 정답 파일의 프로젝트별 `doc_id`로 대조한다

## 재검토

해결: v2 `llm_omitted` 2건은 소유자가 진짜 누락 아님으로 판정했고, #39 채점은 injected만 쓴다(결정 2).

**#39로 미룬 결정** (#39 이슈 본문 "남은 결정"에도 적었다)
- **범위 외 후보 심기**: v2는 범위 외 후보가 0건이다. #39의 "미매핑 작업" 검출을 시험하려면 요구사항과 무관한 업무를 코드가 일부러 심을지 정한다(누락 후보와 같은 방식)
- **"연결 없음" / "비슷한 업무 없음" 구분**: injected 누락 후보의 절반은 비슷한 업무가 있다(Claude 판정 10건 중 5건). #39 채점에서 둘을 나눌지
  (예: 사람이 검수한 "비슷한 업무 없음" 부분 집합을 따로 둔다) 정한다
