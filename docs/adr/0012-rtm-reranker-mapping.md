# ADR-0012: RTM 연결은 요구사항×업무 리랭커 점수 + 고정 기준값 0.5, 누락 정답은 사람 검수 4범주로 채점

- 상태: 채택 (2026-10-18)
- 이슈: #39
- 결정한 사람: 소유자(miin-jun)
- **소유자가 직접 구현**: 연결 판정 함수 `src/rfp_pm_agent/rtm/mapping.py`(`build_rtm`)는 소유자가 직접 짰다. Claude는 점수표·실행·채점 코드와 테스트·문서를 맡았다
- 관련: [ADR-0002](0002-reranker.md)(리랭커 bge-reranker-v2-m3), [ADR-0008](0008-synthetic-pms-and-rtm-truth.md)(합성 PMS와 RTM 정답, `injected`·`llm_omitted`),
  [ADR-0009](0009-pms-query-tools.md)(지연 판단 `pms/rules.py`), data-design.md 6절(지연 정의)·7절(누락 정답 검수·채점 규칙)

## 맥락

- RTM은 요구사항마다 연결된 업무·상태·지연·산출물을 묶은 표다. 연결이 없는 요구사항은 **누락 후보**, 연결이 없는 업무는 **범위 외 후보**다(architecture.md "RTM")
- 합성 PMS v2는 요구사항 50건(`injected`)의 업무 연결(`wbs_requirements`)을 일부러 지웠다. 정답의 뜻은 "연결이 없다"이지 "비슷한 업무가 없다"가 아니다(ADR-0008 "한계")
- RTM은 `wbs_requirements`를 보지 않고 요구사항 원문과 업무 이름만으로 연결을 다시 만들어야 한다 — 그래야 지운 연결을 누락으로 찾는지 잴 수 있다

## 결정

### 1. 연결 방식 B: 요구사항 원문과 업무를 비교해 연결을 추론하고, DB 연결은 채점에만 쓴다

| 방식 | 내용 | 판단 |
|---|---|---|
| A | DB 연결(`wbs_requirements`)을 그대로 읽어 RTM을 만든다 | 버림 — 정답을 읽어 정답과 비교하는 셈이라 정확도가 항상 100%로 무의미하다 |
| **B** | 요구사항 원문과 업무를 비교해 연결을 추론한다. DB 연결은 채점에만 쓴다 | **채택** |
| C | A와 B를 섞는다 | 버림 — 어느 연결이 추론이고 어느 것이 DB인지 나눠 채점해야 해 채점이 복잡하다 |

B를 고른 이유: 이 프로젝트의 문제 정의가 "요구사항과 진행 상황이 분리 관리되어 누락과 범위 분쟁이 생긴다"(architecture.md, #39 목적)이다 — 연결이 없는 상태에서
**연결을 만들어 주는 것이 RTM의 기능**이다. 이미 연결된 DB를 읽기만 하면 그 기능을 보여 주지 못한다. (A·B·C와 이유는 소유자가 정했다)

B 안에서 비교는 요구사항×업무 모든 쌍의 리랭커 점수 + 고정 기준값으로 한다:

- 사업마다 요구사항 전체 × 그 사업의 업무(level 1 단계 업무 제외) 모든 쌍 = **15,446쌍**(요구사항 416건)
- query = 요구사항 원문(`data/parsed` `Requirement.text`, 검수표와 같은 원문), document = 업무 이름. 리랭커는 검색에 쓰는 TEI `bge-reranker-v2-m3`(ADR-0002)를 그대로 쓴다
- 점수는 `scripts/build_rtm_scores.py`가 한 번 계산해 `data/eval/rtm_scores_v1.csv`에 저장한다(로컬 TEI 177초, 실패 0건). RTM 생성·채점은 이 파일만 읽고 리랭커를 다시 부르지 않는다.
  이 파일(1.2MB)은 pre-commit 큰 파일 검사(500KB)에 걸려 **git에 넣지 않는다**(소유자 결정). 채점에 쓴 파일의 sha256은 `70d9a162fe43978e1bcb6d0b17b35e6dfc02d44c7e22913e02630de2c7f098b5`(결과 JSON `inputs`에도 있음)이고,
  다시 만들려면 `docker compose up -d tei-rerank` 후 `uv run python scripts/build_rtm_scores.py`. **다시 계산해 같은 sha256이 나오는지는 확인하지 않았다** — GPU fp16 계산이라
  점수 끝자리가 달라질 수 있고, 그러면 기준값 0.5 근처의 연결이 바뀔 수 있다
- 판정(`build_rtm`): 점수 ≥ 0.5인 업무는 **전부** 연결, 요구사항별 최고 점수 < 0.5면 누락 후보, 어느 요구사항과도 연결되지 않은 업무는 범위 외 후보
- 근거: 연결마다 리랭커 점수와 요구사항의 근거 청크 ID(`<doc_id>:block_requirement:<요구사항 ID>`, 색인 청크 파일에 416건 모두 있음)

비교 수단으로 리랭커를 쓴 이유:
- **LLM 비용 0** — 리랭커는 로컬 TEI라 OpenAI 예산을 쓰지 않는다. 쌍마다 LLM으로 판정하면 1만 5천 회가 넘는다
- **이미 고른 모델 재사용** — 한국어 RFP 검색에서 고른 리랭커(ADR-0002)를 그대로 쓰므로 새 의존성이 없다
- **설명 가능** — 연결마다 점수가 있어 "왜 이었는가"를 숫자로 보여 준다. 같은 점수표 파일이면 같은 RTM이 나온다(점수표 재계산의 동일성은 위처럼 미확인)
- **기준값 하나로 판정** — 짝짓기 규칙이 단순해 연습 세트 분포만으로 정할 수 있다(결정 3)

### 2. 누락 정답은 사람이 4범주로 검수한다

`injected` 50건마다 소유자가 요구사항 원문과 그 사업의 업무 전체를 보고 판정했다(2026-10-18, `data/eval/rtm_injected_judgment.csv`).
검수표 `rtm_injected_review.csv`·`.md`에는 유사도·점수·정렬 같은 판단을 끌어갈 정보를 넣지 않았다.

| 판정 | 건수 | 뜻 | 채점 |
|---|---|---|---|
| 없음 | 5 | 비슷한 업무가 없다 = **진짜 누락** | RTM이 누락 후보로 표시해야 정답 |
| 애매 | 31 | 관련 업무는 있으나 요구사항 일부가 빠졌거나 불명확 | RTM이 업무를 하나라도 이으면 정답 |
| 있음 | 13 | 비슷한 업무가 있다 | RTM이 업무를 하나라도 이으면 정답 |
| 해당없음 | 1 | 업무로 수행할 요구사항이 아니다 | 채점 제외 |

**해당없음을 둔 이유**: PRJ-01 COR-001("표준제약")은 계약상 책임 조항이라 대응하는 업무가 원래 없다. "없음"으로 두면 RTM이 누락으로 부르지 않을 때
오답이 되고, "있음"으로 두면 아무 업무나 이어도 정답이 된다 — 어느 쪽도 RTM의 능력을 재지 못해 뺐다.

검수 결과 **진짜 누락은 5/50**뿐이다. 연결을 지운 요구사항 대부분(44건)에 비슷한 업무가 남아 있었다 — `injected` 전체를 "누락이어야 정답"으로 채점하면
RTM이 맞게 이은 것을 틀렸다고 센다. ADR-0008의 Claude 표본 판정(10건 중 5건 비슷한 업무 있음)보다 사람 검수의 "있음·애매" 비율이 높다.

### 3. 기준값 0.5는 연습 세트 분포로 측정 전 고정

- **연습 세트** = `injected`가 아닌 요구사항 366건(연결 정답 930쌍이 있다). **시험 세트** = `injected` 50건. 기준값을 정할 때 시험 세트 점수는 보지 않았다
- 연습 세트 쌍 점수: 진짜 짝(930쌍) 중앙값 0.683(25% 0.351, 75% 0.873), 짝 아닌 쌍(12,657쌍) 중앙값 0.255(25% 0.042, 75% 0.654)
- 연습 세트 요구사항별 최고 점수(366건): 최솟값 0.156 · 5% 0.475 · 10% 0.644 · 25% 0.804 · 중앙값 0.886

| 기준값 | 최고 점수 < 기준(연습 366건 중 누락으로 잘못 부르는 수) |
|---|---|
| 0.3 | 7 (1.9%) |
| **0.5** | **20 (5.5%)** |
| 0.7 | 51 (13.9%) |
| 0.9 | 203 (55.5%) |

0.5는 연결이 있는 요구사항을 누락으로 잘못 부르는 비율을 5% 안팎(요구사항별 최고 점수의 5% 지점 0.475)에 두는 값이고, 진짜 짝 중앙값과 짝 아닌 쌍 중앙값 사이에 있다.
0.7부터는 잘못 부르는 수가 두 배 이상 늘어난다. 시험 결과를 본 뒤 기준값을 바꾸지 않는다(채점은 한 번만, `run_rtm_eval`은 결과 파일이 있으면 멈춘다).

### 4. 지연·산출물은 기존 규칙을 그대로 쓴다

업무 상태·계획/실적 날짜·산출물은 PMS DB(읽기 전용 계정)에서 읽고, 지연·지연 일수·기한 지난 미제출은 `pms/rules.py`(data-design.md 6절, 조회 툴 #21과 같은 함수)로
`AS_OF_DATE` 기준으로 판단한다. 출력은 `RTM_OUT_DIR`/rtm_<project_id>.md·.csv(`uv run python -m rfp_pm_agent.rtm.report`).

## 결과 (2026-10-18, `data/eval/results/rtm/rtm_eval_v1.json`, 1회 실행)

| 세트 | 결과 |
|---|---|
| 시험 — 없음(진짜 누락) | **0/5 — 미통과** (누락 후보로 표시한 것 0건) |
| 시험 — 있음·애매 | 44/44 업무 연결 |
| 시험 — 전체(해당없음 1건 제외) | 44/49 |
| 연습 — 누락으로 잘못 부른 수 | 19/364 (`llm_omitted` 2건 제외) |
| `llm_omitted` (정답 아님, 따로 표기) | PRJ-06 PSR-003 연결됨 · PRJ-09 PSR-001 누락 후보 |

- RTM 전체: 요구사항 416건, 연결 5,547개(요구사항당 평균 13.3개), 누락 후보 20건(연습 19 + PRJ-09 PSR-001), 범위 외 후보 1건(PRJ-08 2.5 "종자 투하장치 설계")
- **진짜 누락 검출 0/5 — 미통과.** 진짜 누락 5건 모두 업무가 하나 이상 0.5 이상으로 이어졌다(아래 "원인")
- **연결 쌍 정확도**(연습 세트, `injected` 제외 — 시험 세트는 보지 않음): RTM이 이은 4,935쌍 중 정답(`wbs_requirements`) 618쌍 → **정밀도 12.5%**, 정답 930쌍 중 618쌍 → **재현율 66.5%**.
  채점 코드(`run_rtm_eval`)는 누락 판정만 보므로 이 숫자는 점수표와 `pms_v2.json`으로 따로 계산했다(채점 뒤 코드를 바꾸지 않으려고 넣지 않음)
- "있음·애매 44/44"는 능력을 보여 주는 숫자로 읽기 어렵다 — 요구사항당 평균 13개 업무를 잇는 상태에서는 "하나라도 이으면 정답" 규칙을 거의 항상 통과한다
- 이슈 완료 기준 "미매핑 요구사항 최소 1건 검출(시드에 심어 확인)" — **미통과**. 누락 후보는 숫자상 20건이지만 모두 연습 세트(연결 정답이 있는 요구사항) 19건과 `llm_omitted` 1건이고, 일부러 심은 요구사항(injected 50건)은 0건이다
- 비용: OpenAI $0 (리랭커는 로컬 TEI)

## 원인 (사후 분석 — 기준 변경 아님)

채점 뒤 결과 파일(`rtm_eval_v1.json`)과 점수표로 본 **분석**이다. 이 분석을 보고 기준값·규칙을 바꾸지 않았다. 진짜 누락 5건 각각:

| 요구사항 | 최고 점수 | 최고 점수 업무 | 0.5 이상 업무 수 |
|---|---|---|---|
| PRJ-01 ECR-002 가상화 PC OS 업그레이드 | 0.768 | 2.1 요구사항 및 산출물 관리체계 설계 | 2 |
| PRJ-02 SER-001 정보보안교육 실시 | 0.900 | 1.2 요구사항 상세화 및 추적 | 3 |
| PRJ-03 DAR-001 연계 데이터 형식 | 0.771 | 1.2 요구사항 분석 및 추적 관리 | 2 |
| PRJ-06 COR-004 감리 대응 | 0.758 | 1.8 데이터·보안·제약 분석 | 1 |
| PRJ-09 SER-004 용역수행 관련 보안관리 | 0.904 | 1.6 성능 및 보안 요구 분석 | 19 |

5건 모두 최고 점수 업무가 분석·설계 단계의 이름이 넓은 업무다("요구사항 … 추적", "… 요구 분석"). 이런 업무가 관련 없는 요구사항과도 0.75~0.90을 받아
기준값 0.5로는 누락이 드러나지 않았다. 개선은 #96(RTM 누락 검출 개선)에서 다룬다.

## 한계

- **범위 외 검출은 단위 테스트로만 확인했다.** 합성 PMS v2에는 요구사항이 연결되지 않은 업무가 0건이라(ADR-0008) 실데이터로 잴 정답이 없다.
  가짜 데이터에 무관한 업무를 심어 `out_of_scope`로 나오는지만 확인했다(`tests/unit/test_rtm_mapping.py`·`test_rtm_report.py`). 실데이터에서 나온 1건(PRJ-08 2.5)은 정답 기준으로는 오탐이다
- **사업관리·계약·보안 요구사항 점수가 낮다.** 연습 세트에서 누락으로 잘못 부른 19건 중 사업관리(PMR 7·PSR 3) 10건, 계약(COR) 4건, 보안(SER) 1건이고,
  사업으로는 PRJ-09 13건·PRJ-05 5건에 몰렸다. 보고·일정·보안 관리 요구사항의 원문과 "착수 보고" 같은 업무 이름 사이의 점수가 낮게 나온다
- **이름이 넓은 업무가 아무 요구사항과도 높은 점수를 받는다.** "요구사항 상세화 및 추적", "성능 및 보안 요구 분석" 같은 분석 단계 업무가 관련 없는 요구사항과 0.75~0.90을 받아
  진짜 누락을 가렸다("원인" 표). document가 업무 이름 몇 단어뿐이라 생기는 것으로 보이지만 원인은 확인하지 않았다
- **진짜 누락 표본이 5건뿐이다.** 0/5는 이 설정이 진짜 누락을 못 잡는다는 신호로는 충분하지만, 방식을 바꾼 뒤의 개선 폭을 비교하기에는 표본이 작다
- 검수는 소유자 한 사람이 했다. "애매"(31건)의 경계는 사람마다 다를 수 있다

## 재검토

- 진짜 누락을 잡으려면 기준값이 아니라 **방식**을 바꿔야 한다(기준값을 올리면 연습 세트 오탐이 0.7에서 51건으로 먼저 는다) → **#96 RTM 누락 검출 개선**.
  후보 방향(실행 안 함): 요구사항별 상위 몇 개 후보만 LLM이 "이 업무가 요구사항을 수행하는가"를 판정, 상대 점수(업무별 평균으로 보정해 넓은 업무를 낮추기 등)
- 시험 50건은 결과(0/5)를 본 뒤라 다시 "시험"으로 쓸 수 없다 — 방식은 연습 세트로 정하고, 새 검증 세트(다른 seed로 심고 다시 검수)로 한 번만 채점한다(#96)
