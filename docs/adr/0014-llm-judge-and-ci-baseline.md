## 맥락

- #19 근거 답변 평가는 "거절했나·출처가 형식에 맞나"만 코드로 셌고, 답이 맞는지는 사람이 표를 보고 판단했다. PR마다 사람이 62문항을 볼 수 없다

## 결정

### 1. 채점 방식 — `judge_v1` (`src/rfp_pm_agent/eval/answer_judge.py`, `eval/prompts/judge_v1.md`)

- 문항마다 **답 정확성**(`answer_correct`: qa_v2 정답의 핵심 사실을 빠짐없이·틀리지 않게 담았나)과 **인용 근거성**(`citation_supported`: 답 내용이 인용한 청크 원문에 있나)을
  **따로** 판정하고 `reason` 한 줄을 받는다. 출력은 JSON 하나이고 Pydantic으로 검증한다. 형식 오류는 재시도하지 않고 원문과 함께 기록한다
- **거절은 LLM 없이 규칙으로 판정**: 정답 없는 문항(답 없음·무관)은 거절이면 맞음, 정답이 있는데 거절이면 틀림. 인용이 없으면 LLM 판정과 상관없이 근거성은 거짓
- 채점 프롬프트는 파일 이름이 버전이다. 바꾸면 `judge_v2`를 새로 만들고 기준선을 다시 정한다(기준선 검사가 채점 프롬프트 불일치를 실패로 잡는다)

### 2. 채점 모델 — `gpt-6-sol`

- 답을 만든 모델(`gpt-6-luna`)로 채점하면 자기 답의 표현·실수를 맞다고 보기 쉽다(자기 채점 편향). 그래서 답 모델과 다른, 상위 모델을 골랐다
- 단가(2026-10-19 공식 가격표·모델 페이지): 입력 $2.00 / 출력 $10.00 per 1M, 추론 강도 low(`LLM_REASONING_EFFORT`). 실측 채점 1회(42~45호출) $0.13~0.15
- 후보 비교(2026-10-19, 42회 추정): gpt-6-luna 약 $0.01, gpt-5.6-luna 약 $0.02, gpt-6-sol·gpt-6.1-sol 약 $0.18, gpt-5.6-terra 약 $0.19, gpt-6-astra 약 $0.90
- 설정: `LLM_MODEL_JUDGE`, `LLM_JUDGE_PRICE_INPUT_PER_1M`, `LLM_JUDGE_PRICE_OUTPUT_PER_1M`. 비용 로그는 채점 단가로 계산한다(`ClientsConfig.for_judge`)

### 3. 사람 판정과 대조

- `replay_v2` 결과(2026-10-15)에서 10문항을 코드로 골랐다(`eval/judge_sample.py`, 묶음별 개수 고정 + 시드 25: 정답 청크 인용 1개 2·여러 개 3·정답 청크 미인용 2·잘못 거절 2·답 없음 거절 1)
- 판정지에는 묶음 이름과 LLM 결과를 넣지 않았고, **사람 판정을 LLM 채점 전에 커밋했다**(7315ced)

| 항목 | 일치 |
|---|---|
| 답 맞음 | 9/10 |
| 출처 맞음 | 7/7 (인용 없는 3문항은 사람이 '-'로 두어 제외) |

- 불일치 q020(답 맞음, 사람 O · LLM X): 정답 "착수일로부터 약 4개월인 2026년 12월 31일까지", 시스템 답 "계약일로부터 약 4개월간 … 2026년 12월 31일까지".
  LLM은 "기간의 기준을 착수일이 아닌 계약일로 답했다"며 틀림으로 봤다. 원문 청크는 "착수일로부터 약 4월간 (계약일 ~ 2026년 12월 31일)"로 두 표현이 함께 있다 — LLM이 사람보다 엄격한 쪽

### 4. 측정 전 정답 수정 (2468451, 사용자 승인)

- q013: 같은 금액이 "소요금액 : 금99,110천원(부가세 포함)"으로 적힌 b0022도 정답 청크. evidence를 세 청크 공통 원문 조각 `금99,110천원(부가`로 줄였다
- q007: "기술 90%·가격 10%"만 답해도 정답. evidence에 대안 문자열 목록(OR)을 허용하도록 `EvalQuestionV2`를 늘려 "기술평가(90%), 가격평가(10%)" 문단(b0048·b0007)을
  정답 청크에 넣었다. 문단으로도 답할 수 있어 `table` 태그를 뺐다. answer·note에 기준을 적었다
- 두 수정 모두 LLM 채점 전에 커밋했다. 점수를 보고 바꾼 것이 아니다

### 5. 기준선과 허용 오차 (`data/eval/baseline.json`)

같은 코드(9b300db)로 근거 답변 62문항을 3회 생성하고 각각 `judge_v1`로 채점했다(답변 `gpt-6-luna`·`grounded_answer_v2`·doc 범위·`rfp_chunks_v2_kure`).

| 회차 | 정답(답 있음 51) | 출처 정확도 | 잘못 거절(51 중) | 그중 A | 답 없음·무관 거절 |
|---|---|---|---|---|---|
| r1 | 36 (70.6%) | 44/44 | 7 | 1 | 11/11 |
| r2 | 34 (66.7%) | 44/44 | 7 | 2 | 11/11 |
| r3 | 36 (70.6%) | 44/45 (0.978) | 6 | 2 | 11/11 |
| 평균 (최소~최대) | 69.3% (34~36) | 0.993 (0.978~1.0) | 6.7 (6~7) | 1.7 | 11 |
| replay_v2 (10-15 답변) | 33 (64.7%) | 42/42 | 9 | 2 | 11/11 |

- 검색 결과는 3회 모두 같았다(입력 토큰 359,398). 62문항 중 41문항의 답 문장이 회차마다 달랐고, 정답 판정이 바뀐 문항은 7개(q015·q020·q025·q027·q041·q051·q053, 그중 3개는 거절↔답변)
- **기준(소유자 결정)**: 정답 ≥ 33/51, 출처 정확도 ≥ 0.95, 정답 있는 문항 잘못 거절 ≤ 9, 답 없음·무관 거절 11/11
- 근거: 같은 코드에서도 정답이 ±2문항 흔들린다. 정답 33은 3회 최소(34)보다 1 낮고 replay_v2와 같다. 잘못 거절 9는 3회 최대(7)보다 2 높은 replay_v2 값, 출처 0.95는 3회 최소 0.978 아래 1~2문항 여유. 답 없음·무관은 4번 모두 11/11이라 여유를 두지 않았다

### 6. CI는 결과 파일만 비교한다 (`eval/check_baseline.py`, `.github/workflows/ci.yml`)

- 로컬에서 평가를 돌리면 `answer_judge`가 `data/eval/latest_summary.json`을 다시 쓴다(재생·실험 결과는 `--no-latest`). 이 파일을 커밋한다
- CI는 LLM·OpenSearch 없이 두 가지를 검사한다
  1. latest_summary가 baseline 기준을 못 넘거나 채점 조건(모델·프롬프트·문항 수)이 다르면 실패 — 항목과 값을 메시지로
  2. PR에서 평가 영향 파일(`EVAL_AFFECTING_PATHS`: 검색·답변 코드와 프롬프트, 에이전트 프롬프트, 채점 프롬프트, qa_v2·무관 세트, 인덱스 매핑)이 바뀌었는데 latest_summary가 안 바뀌면 실패 — 재측정 안내
- **CI에서 실제 평가를 돌리지 않는 이유**: OpenSearch(nori)·TEI 2개(GPU)·OpenAI 키가 필요하고, PR마다 약 $0.2(답변 + 채점)가 든다. GitHub 호스트 러너에는 GPU가 없다
- **self-hosted runner 보류 이유**: 공개 레포라 외부인의 PR 코드가 소유자 노트북에서 실행될 수 있고(키·로컬 파일 노출 위험), 노트북을 항상 켜 둬야 한다
- 이후 안전한 러너를 붙여도 `baseline.json`·`check_baseline.py`는 그대로 쓰고, 러너가 평가를 돌려 latest_summary를 만드는 단계만 앞에 붙이면 된다

## 고려한 대안

| 대안 | 판단 |
|---|---|
| 답 모델(`gpt-6-luna`)로 채점 | 채택 안 함 — 자기 채점 편향, 비용 차이는 회당 약 $0.12 |
| 답 정확성과 근거성을 한 점수로 | 채택 안 함 — "맞지만 근거 없음"(외부 지식)과 "근거는 있지만 틀림"을 구별할 수 없다 |
| 기준선 = 3회 평균 | 채택 안 함 — 같은 코드에서도 최소값 아래로 떨어질 수 있어 변동만으로 CI가 실패한다 |
| CI가 latest_summary를 읽지 않고 PR 본문 수치를 확인 | 채택 안 함 — 사람이 적는 값은 검증할 수 없다 |

## 한계

- 사람 대조가 10건이라 일치율(답 9/10)의 불확실성이 크다. 출처는 7건 모두 일치했지만 대조 10건에서 사람·LLM 모두 "근거 없음"을 낸 문항이 없어, 근거 없는 답을 LLM이 잡아내는지는 재지 못했다
- 정답률이 약 70%이고, 오답 15~17개 중 6~7개는 정답이 있는데 거절한 것이다. 기준선은 지금 성능을 지키는 하한이지 목표가 아니다
- latest_summary는 커밋한 사람이 실제로 돌렸다는 것을 CI가 증명하지 못한다(파일 위조·오래된 결과 재사용). 실행 기록(`answers_file`·`judge_file`)과 PR 리뷰로 확인한다
- 검사 2는 경로 목록으로만 판단한다. 목록 밖 파일(예: `clients/`, `config.py` 기본값)이 결과를 바꿔도 잡지 못한다

## 재검토

- 채점 프롬프트·모델을 바꿀 때(기준선 다시 측정), 사람 대조를 늘릴 때(30건 이상 권장), 안전한 평가 러너를 붙일 때
