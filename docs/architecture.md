## 0. 한 문장 요약

실제 공공 SI 사업 제안요청서(RFP)와 그 RFP로 만든 프로젝트 관리 데이터를 근거로,
**"이번 주 지연된 업무가 뭐야?", "데이터 이관 관련 산출물 찾아줘" 같은 질문에 출처를 달아 답하고,
권한에 따라 보이는 문서가 달라지며, MCP로 다른 AI 도구에서도 부를 수 있는 에이전트**를 만든다.
코드는 Claude Code가 짜고, 사람은 **하네스(규칙·검사 장치)를 설계**해 품질을 통제한다.

## 1. MVP란

**MVP(Minimum Viable Product, 최소 기능 제품)** = 핵심 가치를 증명할 수 있는 **가장 작은, 처음부터 끝까지 실제로 동작하는 버전**.

- "기능을 다 조금씩" 만드는 게 아니라, **입력 → 처리 → 출력이 한 줄로 관통**하는 얇은 버전을 먼저 완성하는 것
- 나머지는 그 뼈대 위에 붙여 나감
- 이 프로젝트에서 MVP가 필요한 이유: 정해둔 기간 안에 처음부터 끝까지 실제로 동작하는 결과물을 보여줘야 하기 때문

```
나쁜 순서: 수집 파이프라인 완벽하게 → 파싱 완벽하게 → ... → 마감일에 에이전트 미완성
좋은 순서: 문서 5건으로 전 구간 관통(MVP) → 문서 늘리기 → 권한 추가 → 파이프라인 자동화 → ...
```

| 단계 | 목표 시점 | 범위 |
|---|---|---|
| **Phase 0 — 하네스** | 착수 1~2일 | 레포, `CLAUDE.md`, 훅, CI, 평가 틀 |
| **Phase 1 — MVP** | ~9/27 | RFP 몇 건 → 파싱 → 하이브리드 검색 → 출처 답변 + PMS 조회 툴 + 에이전트 + MCP + 평가 세트 + RTM(요구사항 추적 매트릭스) + 데모 화면 |
| **Phase 2 — 확장** | ~10/20 | 권한(RBAC), 파이프라인 자동화(Airflow·PySpark), Batch API 대량 생성, HWP·Office 확대, 관측, 배포 |
| Phase 3 — 선택 | 여유 있으면 | k3s, Databricks 이식 |

아래 아키텍처 그림에서 각 구성요소 옆에 **[MVP] / [P2] / [P3]** 표시.

### 구성요소가 문제 정의의 어느 부분을 푸는가

| 구성요소 | 푸는 문제 |
|---|---|
| ① 수집·적재 파이프라인 | RFP 원문이 흩어져 있고 형식도 제각각(HWP·HWPX·PDF)이라, 우선 검색 가능한 형태로 모으고 정규화한다 |
| ② 합성 PMS 생성 | 실제 진행 상황(WBS·일정·Risk·산출물) 데이터가 없으므로, 요구사항에 결부된 시연·평가용 진행 데이터를 코드로 만든다 |
| 파싱·청킹 | 요구사항 ID 단위로 원문을 잘라야 "이 업무가 어느 요구사항 때문인지" 검색이 정확해진다 |
| 검색 엔진 (BM25 + 벡터) | 요구사항 ID 같은 정확한 단어와, 다르게 표현된 같은 의미 둘 다 찾아야 대조 누락이 줄어든다 |
| ③ 검색·RAG 서비스 | 요구사항 원문을 근거와 함께 찾아준다 — 사람이 문서를 손으로 대조하지 않아도 되게 |
| 권한 필터 (RBAC) | 실제 SI 현장처럼 역할별로 열람 가능한 문서가 다른 상황을 반영한다 |
| ④ 에이전트 | 문서 검색(RAG)과 PMS 조회를 한 번에 엮어 "지연된 업무 + 관련 요구사항 + 산출물 여부"를 한 질문으로 답한다 — 문제 정의의 핵심 |
| ⑤ 인터페이스 (API·MCP) | 만든 답을 실제로 받아볼 수 있는 통로를 제공한다 |
| ⑥ 평가·관측 | 근거 없는 답(환각)과 요구사항 누락을 사람이 매번 확인하지 않아도 자동으로 잡아낸다 |
| ⑦ 배포 | 로컬 환경에서 처음부터 끝까지 재현 가능하게 만든다 |
| RTM (요구사항 추적 매트릭스) | 질의응답만으로는 요구사항↔작업↔산출물의 전체 연결이 한눈에 안 보인다 — 표로 만들어 누락(미매핑 요구사항)·범위 외(미매핑 작업) 후보를 드러낸다 (#39) |
| 데모 화면 | 레포를 처음 보는 사람이 무엇을 하는 도구인지 바로 파악할 수 있게 질의응답·RTM·검색 비교를 한 화면에 모은다 (#40) |

## 3. 데이터 흐름 예시 — 질문 하나가 처리되는 과정

질문: **"이번 주 지연된 업무랑 관련된 요구사항 문서 알려줘"** (사용자: 개발자 역할)

1. **에이전트**가 질문을 해석 → 두 가지 정보가 필요하다고 판단
2. 툴 1 `get_delayed_tasks(week=이번주)` 실행 → PostgreSQL에서 지연 업무 3건 (예: "데이터 이관 설계", ...)
3. 툴 2 `search_documents("데이터 이관 설계 요구사항")` 실행
   - 권한 필터: 개발자 역할이 볼 수 있는 문서만 대상
   - BM25로 키워드 일치 문서, 벡터 검색으로 의미 유사 문서 → RRF로 합침 → 리랭커로 재정렬
4. 에이전트가 두 결과를 결합해 답변 생성: 업무별 지연 일수 + 관련 요구사항 원문 + **[제안요청서 p.23, DAT-003]** 같은 출처
5. 전 과정이 트레이스로 남고, 평가 세트에 이 질문이 있으면 "툴을 올바른 순서로 불렀는가 / 출처가 맞는가"를 자동 채점

## 4. 핵심 개념

각 개념은 **무엇 → 왜 필요 → 이 프로젝트에서 어디** 순서. 이미 해 본 것은 ✅, 새로 배울 것은 🆕.

### 4-1. 데이터 파이프라인

**ETL / ELT** 🆕 — Extract(추출) · Transform(변환) · Load(적재). 변환을 적재 전에 하면 ETL, 적재 후 저장소 안에서 하면 ELT.

**메달리온 구조 (Bronze / Silver / Gold)** 🆕
- Bronze: 원본 그대로 (다운로드한 HWP·PDF)
- Silver: 정제된 중간 결과 (파싱된 텍스트 + 메타)
- Gold: 바로 쓰는 결과 (청크 + 임베딩 인덱스)
- 왜: 파서를 바꿔도 **원본부터 다시 받을 필요 없이** Silver부터 재처리 가능. 문제가 생긴 단계를 추적 가능

**멱등성(Idempotency)과 증분 처리** ✅(f1-ragops 증분 재색인 경험)
- 멱등성: 같은 작업을 여러 번 실행해도 결과가 같음 → 실패 후 재실행이 안전
- 증분 처리: 바뀐 것만 처리 (파일 해시 비교)

**오케스트레이션 — Airflow** 🆕 [P2]
- DAG(Directed Acyclic Graph): 작업(Task)들과 그 순서(의존성)를 그래프로 정의
- 스케줄 실행, 실패 시 재시도, 실행 이력 UI
- 이 프로젝트: `매일 새 공고 수집 → 다운로드 → 파싱 → 인덱싱` DAG

**Spark / PySpark** 🆕 [P2]
- 데이터를 여러 조각(partition)으로 나눠 **병렬 처리**하는 엔진. PySpark는 그 Python API
- DataFrame API는 pandas와 비슷하지만 **지연 실행(lazy)** — `.count()`, `.write()` 같은 action이 호출될 때 실제 계산
- 정직한 판단: 문서 수백 건은 Spark가 필요 없는 규모. **공고 목록 수만 건 정제·분류**처럼 표 형태 대량 데이터에 적용하는 게 자연스러움
- Databricks는 Spark를 관리형으로 제공하는 플랫폼 → 로컬 PySpark로 짠 코드를 나중에 이식 [P3]

### 4-2. 문서 처리

**파싱(Parsing)** — 파일에서 텍스트와 구조(제목, 표, 페이지)를 꺼내는 것
- PDF ✅: 텍스트 레이어 추출. 표·다단 레이아웃이 깨지기 쉬움
- **HWPX** 🆕: 사실상 ZIP 안의 XML (OWPML 표준) → 압축 풀고 XML 파싱
- **HWP(구형, HWP 5.0)** 🆕: 바이너리 복합 문서 → 전용 라이브러리나 변환 도구 필요. 도구 선택은 스택 결정 때 검증
- docx·xlsx 🆕: Office Open XML (역시 ZIP + XML)

**청킹(Chunking)** ✅
- 긴 문서를 검색 단위로 자르기. 너무 크면 검색이 부정확, 너무 작으면 문맥 손실
- **구조 기반 청킹**: RFP는 "요구사항 ID(예: SFR-001) 단위"로 자르면 의미가 온전함 → F1 조문 단위 청킹과 같은 원리
- 청크마다 **메타데이터**: 문서 ID, 페이지, 섹션, 요구사항 ID, **보안 등급·접근 역할**(권한 필터용)

### 4-3. 검색 (Information Retrieval)

**희소 검색 — BM25** 🆕 (f1-ragops에서는 TF-IDF를 썼음)
- 키워드 일치 기반 점수. TF-IDF의 개선판
- 핵심 직관 세 가지:
  1. 단어가 문서에 많이 나올수록 점수↑, 하지만 **포화**됨 (10번과 20번 차이는 작음)
  2. 드문 단어일수록 가중치↑ (IDF)
  3. 긴 문서는 불리하지 않게 **길이 정규화**
- 강점: 요구사항 ID, 시스템명, 고유명사처럼 **정확한 단어**를 잘 찾음

**한국어 형태소 분석** 🆕
- "이관했습니다" → "이관 + 하 + 었 + 습니다". 형태소로 쪼개야 BM25가 "이관"을 매칭
- Elasticsearch/OpenSearch는 **nori** 분석기 제공 (Kiwi는 이미 써 봄 ✅)

**밀집 검색 — 임베딩 + 벡터 검색** ✅
- 문장을 벡터로 바꾸고 **코사인 유사도**로 의미가 가까운 것을 찾음. 표현이 달라도 의미가 같으면 찾음
- **ANN(근사 최근접 탐색) — HNSW** 🆕: 모든 벡터와 비교하지 않고 그래프를 타고 가까운 후보만 탐색 → 빠르지만 100% 정확하진 않음

**하이브리드 검색과 RRF** ✅
- BM25(정확한 단어) + 벡터(의미)의 약점을 서로 보완
- RRF(Reciprocal Rank Fusion): 점수 대신 **순위**로 합침 → `score(d) = Σ 1 / (k + rank(d))`, 보통 k=60
- 점수 척도가 다른 두 검색기를 정규화 없이 합칠 수 있는 게 장점

**리랭킹** ✅
- Bi-encoder(임베딩 검색): 질문과 문서를 **따로** 벡터화 → 빠름, 1차 후보 수백 개
- Cross-encoder(리랭커): 질문과 문서를 **같이** 넣어 관련도 판단 → 느리지만 정확, 상위 20~50개만 재정렬

**검색 평가 지표** ✅ — Recall@k(정답이 상위 k개에 있나), MRR(첫 정답의 순위 역수 평균), NDCG(순위별 가중 점수)

### 4-4. RAG와 근거 기반 답변 (Grounded RAG)

- RAG: 검색한 문서를 LLM 입력에 넣어 답하게 하는 구조
- **Grounded**: 답의 각 주장이 **검색된 원문에 근거**해야 하고, 그 근거(문서·페이지·요구사항 ID)를 **출처로 표시**
- **근거 없으면 거절**: 검색 결과에 답이 없으면 "문서에서 찾을 수 없음"이라고 답하게 설계 → 환각(Hallucination) 억제
- 평가: **Faithfulness(근거 충실도)** — 답의 문장이 컨텍스트에서 지지되는가, **Citation 정확도** — 달린 출처가 실제 근거인가

### 4-5. 권한 반영 검색 (RBAC) 🆕 [P2]

- RBAC(Role-Based Access Control): 사용자 → **역할**(PM, 개발자, 고객사, 외부 협력사) → 역할별 **접근 가능한 자원**
- 문서/청크마다 `allowed_roles`, `security_level` 메타데이터
- **사전 필터(Pre-filter) vs 사후 필터(Post-filter)** — 이 프로젝트의 핵심 설계 포인트
  - 사후 필터: 전체 검색 → top-k 뽑은 뒤 권한 없는 것 제거 → **top-k가 텅 빌 수 있고**, 제거 전 결과가 로그·리랭커·LLM에 새어 나갈 위험
  - 사전 필터: 검색 **쿼리 자체에 권한 조건**을 넣음 → 볼 수 있는 문서 안에서만 top-k
  - → **사전 필터 채택**
- 평가: **권한 유출 테스트** — 권한 없는 역할로 질문해 제한 문서가 한 건도 안 나오는지 자동 검사 (회귀 게이트에 포함)

### 4-6. 정형 데이터 질의 — Text-to-SQL vs 정해진 툴 🆕

| 방식 | 설명 | 장점 | 위험 |
|---|---|---|---|
| Text-to-SQL | LLM이 SQL을 직접 작성 | 어떤 질문이든 대응 | 틀린 SQL, 권한 우회, 데이터 변경 위험 |
| **정해진 툴** | `get_delayed_tasks(week)` 처럼 파라미터화된 쿼리를 툴로 제공 | 정확·안전·테스트 가능 | 미리 정의한 질문만 가능 |

- MVP는 **정해진 툴** 위주. 확장 시 **읽기 전용 DB 계정 + 허용 테이블 제한**을 둔 Text-to-SQL을 보조로 추가하는 선택지
- 공고의 예시 질문(지연 업무, 미해결 Risk, 산출물)은 툴로 충분히 커버됨

### 4-7. 에이전트

**Tool / Function Calling** ✅
- LLM이 직접 실행하는 게 아님. LLM은 **"이 툴을 이 인자로 불러라"라는 JSON을 생성**만 하고, **코드가 실행**해 결과를 다시 LLM에 넣음
- 툴 이름·설명·인자 스키마가 곧 LLM이 읽는 API 문서 → **툴 설명 품질이 툴 선택 정확도를 좌우**

**ReAct 루프** — 생각(Reason) → 행동(Act, 툴 호출) → 관찰(Observe) → 반복 → 최종 답변. 멀티스텝 에이전트의 기본 형태

**LangGraph** ✅(교육과정 실습) → 이번에 실제 서비스로
- **State**: 대화·중간 결과를 담는 공유 상태
- **Node**: 한 단계(LLM 호출, 툴 실행)
- **Edge / Conditional Edge**: 다음 노드로 가는 규칙 (조건 분기)
- **Checkpointer**: 상태 저장 → 대화 이어가기, 중단 후 재개
- **HITL(Human-in-the-Loop)**: Issue 등록 같은 **쓰기 동작은 사람 승인 후** 실행

**에이전트 평가** 🆕
- 최종 답이 맞는가(Task Success)뿐 아니라 **과정(Trajectory)**도 채점: 올바른 툴을 골랐나, 불필요한 호출은 없었나, 단계 수·지연·비용

### 4-8. MCP (Model Context Protocol) 🆕

- AI 앱이 외부 도구·데이터에 붙는 **표준 규격**. "AI용 USB-C"
- 구성: **Host**(Claude Desktop 같은 AI 앱) → **Client**(호스트 안의 연결 모듈) → **Server**(우리가 만드는 것)
- 서버가 노출하는 것: **Tools**(실행 가능한 함수), **Resources**(읽을 수 있는 데이터), **Prompts**(재사용 템플릿)
- 전송 방식: **stdio**(로컬 프로세스) / **Streamable HTTP**(원격)
- 이 프로젝트: 에이전트의 툴을 MCP 서버로도 노출 → Claude Desktop·Claude Code에서 "우리 프로젝트 지연 업무 알려줘"가 동작
- **보안**: MCP 툴은 LLM이 스스로 호출 여부를 결정 → 부작용 있는 툴(삭제·등록)을 열면 **프롬프트 인젝션이 곧 데이터 조작**. MVP는 **읽기 전용 툴만** 노출 (인프라 계획 ADR-3과 같은 원칙)

### 4-9. LLM 대량 처리 — Batch API와 구조화 출력 🆕 [P2]

- **Batch API**: 요청 수백~수천 건을 JSONL 파일로 묶어 제출 → 비동기로 처리(최대 24시간) → 결과 파일 수거. 실시간 API 대비 **비용 50% 할인**
- 실시간 응답이 필요 없는 **합성 PMS 생성, 문서 요약·메타데이터 추출**에 적합
- **구조화 출력(Structured Outputs)**: JSON 스키마를 지정해 그 형식으로만 답하게 함 → Pydantic으로 검증 → 날짜 역전(종료일 < 시작일) 같은 **논리 오류는 코드로 추가 검증**

### 4-10. 평가와 LLMOps ✅(f1-ragops) → 에이전트까지 확장

- **골든셋(Golden Set)**: 질문 + 정답 문서/정답 답변 + 기대 툴 호출 순서
- **LLM-as-Judge**: LLM이 답변 품질을 채점. 채점 기준(루브릭)을 명시하고, 일부는 사람이 검수해 채점 LLM 자체를 검증
- **회귀 게이트**: PR마다 평가를 돌려 **기준선보다 떨어지면 머지 차단**
- **관측(Observability)** [P2]: 요청마다 트레이스(어떤 툴을 어떤 인자로, 몇 초, 몇 토큰) 기록 → Langfuse 같은 도구
- **프롬프트·모델 버전 관리**: 프롬프트를 코드처럼 버전으로 관리하고 평가 결과와 함께 기록

### 4-11. 하네스 엔지니어링 🆕

**"Agent = Model + Harness"** — 같은 모델이라도 주변 장치(하네스)에 따라 결과 품질이 달라진다는 관점

| 구분 | 역할 | 이 프로젝트의 장치 |
|---|---|---|
| **Guides** (피드포워드) | 에이전트가 **행동하기 전**에 방향을 잡음 | `CLAUDE.md`(규칙·명령어·금지사항), `docs/architecture.md`, 스킬 |
| **Sensors — Computational** | **행동한 후** 빠르고 결정적으로 검사 | ruff(린트), mypy(타입), pytest, pre-commit |
| **Sensors — Inferential** | 느리지만 맥락을 이해하는 검사 | 코드 리뷰 서브에이전트 |
| **Behaviour Harness** | 기능이 **실제로 맞게 동작**하는지 | RAG·에이전트 평가 세트, 권한 유출 테스트 |

- **"Keep quality left"**: 빠른 검사는 커밋 전(pre-commit, Claude Code 훅), 비싼 검사는 CI로
- Claude Code에서 쓰는 구성요소:
  - `CLAUDE.md` — 세션마다 읽는 프로젝트 규칙
  - `.claude/settings.json` — 권한(허용·차단 명령), 훅 설정
  - **Hooks** — 특정 시점에 자동 실행되는 명령 (예: 파일 수정 후 ruff·mypy 자동 실행, 작업 종료 시 테스트)
  - **Skills / 커스텀 커맨드** — 반복 작업 절차 (예: "평가 돌리고 결과 비교")
  - **Subagents** — 역할이 분리된 보조 에이전트 (예: 리뷰 전담)
  - **MCP** — Claude Code에 우리 MCP 서버를 붙여 개발 중에도 사용
- 측정할 것: 훅·게이트가 잡아낸 오류 건수, Claude Code 작업의 CI 첫 통과율 등

### 4-12. 배포

- **Docker Compose** ✅: api · mcp · postgres · 검색엔진 · (airflow)를 한 파일로 정의해 한 번에 실행
- **환경변수·시크릿 관리**: API 키는 `.env`(커밋 금지) + `.env.example`만 커밋, `gitleaks` 훅으로 유출 차단
  - ※ 기존 OpenF1 비밀번호 git 히스토리 노출 전례 → Phase 0에서 먼저 설정
- AWS EC2 [P2]: 기존 배포 경험 활용 ✅
