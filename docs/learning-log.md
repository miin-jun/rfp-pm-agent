## 2026-09-13 — gitleaks가 오래된 rev라 가짜 키를 못 잡음

**무슨 일**: 이슈 #6에서 `.pre-commit-config.yaml`에 gitleaks를 추가했는데, 가짜 `OPENAI_API_KEY=sk-...` 키를 넣은 파일을 커밋해도 "Detect hardcoded secrets ... Passed"로 통과했다.

**원인**: pin한 `rev: v8.0.0`(2021년 릴리스)에는 `openai-api-key` 탐지 규칙이 아직 없었다. 훅 자체는 정상 실행됐고 "Passed"까지 찍혔기 때문에, 로그만 보면 정상으로 착각하기 쉬웠다.

**배운 것**: pre-commit 훅이 "Passed"라고 초록불을 켜는 것과 "실제로 탐지 규칙이 최신이라 뭔가를 잡아낼 수 있는 상태"는 별개다. `uv run pre-commit autoupdate`로 `v8.30.0`까지 올린 뒤 같은 가짜 키로 다시 커밋을 시도해 exit code 1로 실제 차단되는 것을 확인했다. 앞으로 보안·품질 관련 훅을 새로 추가하거나 버전을 바꿀 때는 "Passed 뜨는 것"이 아니라 "의도한 위반을 넣었을 때 실제로 막히는 것"을 기준으로 검증한다.

## 2026-09-13 — 훅과 pre-commit의 mypy 검사 범위가 달라 같은 오류가 한쪽에서만 잡힘

**무슨 일**: 이슈 #7에서 `tests/unit/test_smoke.py`에 일부러 타입 오류(`def f(x: int) -> str: return x`)를 심었다. Claude Code의 `post_edit_check.sh` 훅은 즉시 잡아 편집을 막았는데, 그 상태로 실제 `git commit`을 해보니 pre-commit의 mypy 훅은 "Passed"로 통과해버렸다.

**원인**: `post_edit_check.sh`는 방금 수정한 파일 경로를 그대로 `mypy`에 넘겨 검사하지만(`tests/`도 포함), `.pre-commit-config.yaml`의 mypy 훅과 CLAUDE.md 명령어는 둘 다 `mypy src`만 실행해 `tests/`는 애초에 검사 대상이 아니었다. 검사 층(Claude Code 훅 / pre-commit / CI)마다 스코프가 달랐던 것.

**배운 것**: 같은 도구(mypy)를 여러 층에 걸어 두면, 층마다 검사 범위가 다를 수 있고 그러면 "어느 한 층만 통과"가 "전체가 안전"을 의미하지 않게 된다. `mypy src` → `mypy src tests`로 pre-commit·CLAUDE.md 명령을 맞추고, `tests/*`는 `disallow_untyped_defs`만 완화하는 override를 추가해 나머지 strict 규칙은 그대로 유지했다. 부수 효과로 `rfp_pm_agent`에 `py.typed`가 없어 mypy가 내던 `import-untyped` 경고도 `py.typed` 추가로 해소됨을 확인했다(`uv build`로 wheel에 실제 포함되는 것까지 확인). 검사 층을 여러 개 둘 때는 항상 "범위가 서로 같은지"를 먼저 맞춘다.

## 2026-09-14 — 권한 규칙은 도구 호출 경로만 막고, 스크립트가 직접 여는 파일은 못 막음

**무슨 일**: 이슈 #7에서 `.claude/settings.json`의 `deny: ["Read(./.env)", ...]`가 실제로 `.env`를 막는지 직접 시험했다. `cat .env`, `head .env`, `grep .env`, `Read` 도구로 `.env` 열기는 전부 차단됐다. 그런데 `python3 -c "open('.env').read()"`는 **차단되지 않고 그대로 성공**했다 (866바이트 읽힘).

**원인**: permission 규칙은 Claude가 호출하는 도구(Bash 명령어 문자열, Read/Edit 파일 경로)를 문자열 패턴으로 매칭해서 막는다. `python3` 프로세스가 자기 파일 I/O로 직접 `.env`를 여는 것은 이 매칭 레이어를 아예 거치지 않으므로 규칙이 적용될 여지가 없다.

**배운 것**: 방어 장치를 넣었으면 "의도한 경로"만 시험하지 말고 "그 장치가 안 보는 경로"까지 시험해야 실제 방어 범위를 알 수 있다 (gitleaks rev, mypy 스코프에 이은 같은 패턴의 세 번째 사례). 이번 경우 진짜 구멍(스크립트 직접 오픈)은 permission 문자열 패턴으로는 못 막고 OS 수준 격리(샌드박스, docs/harness.md 4절)가 있어야 막힌다 — 후속 이슈 #33으로 분리.

## 2026-09-15 — `.env`를 읽는 코드가 레포 어디에도 없어 모든 설정이 기본값으로만 동작

**무슨 일**: 이슈 #10 검증 중 실행 로그에 `serviceKey=`가 비어 있는 것을 발견했다. `.env`에 `NARA_API_KEY`가 분명히 있는데도 `os.environ`에 올라오지 않았다. grep으로 확인해 보니 `dotenv` 관련 코드가 레포 전체에 하나도 없었다 — `config.py`는 `os.environ.get(...)`으로 값을 "읽기"는 했지만, 애초에 `.env` 파일을 프로세스 환경변수로 로드하는 코드가 없었던 것.

**원인**: `.env.example`을 만들고 `config.py`에서 `os.environ.get()`으로 읽는 코드까지 있으면 "설정이 동작한다"고 착각하기 쉽다. 하지만 `.env` 파일 자체는 셸이 알아서 읽어주는 게 아니다 — `python-dotenv` 같은 라이브러리로 명시적으로 로드해야 `os.environ`에 들어간다. 이슈 #9(모델 클라이언트)를 포함해 지금까지 만든 모든 설정값이 이 문제로 계속 하드코딩된 기본값으로만 동작하고 있었다. 기본값들이 우연히 그럴듯해서(예: `LLM_BASE_URL`의 OpenAI 기본 주소) 드러나지 않았고, **기본값이 있을 수 없는 인증키(`NARA_API_KEY`)에서 처음으로 드러났다**.

**배운 것**: "설정 파일을 만들었다"와 "그 값이 실제로 코드에 도달한다"는 다른 이야기다. `config.py` 맨 위에 `load_dotenv(override=False)` 한 줄을 추가하고, 실제 새 프로세스(`uv run python -c ...`)로 `.env`가 있을 때/없을 때, 셸에 이미 값이 있을 때 각각 실제로 값이 들어오는지 직접 실행해서 확인했다 — 단위 테스트(monkeypatch)만으로는 "라이브러리를 제대로 불렀는지"까지는 검증되지만 "새 프로세스에서 실제로 동작하는지"는 별개라 두 가지를 다 확인했다. 새 설정값을 추가할 때마다 "이 값이 정말 코드에 도달하는가"를 한 번은 실제로 실행해서 확인한다.

## 2026-09-15 — 추측으로 만든 API 파서·fixture는 curl 한 번으로 전부 틀렸다는 게 드러남

**무슨 일**: 이슈 #10을 처음 구현할 때 나라장터 API 필드명(`bidNtceNo` 등)과 응답 구조를 공식 문서·컨벤션 추정만으로 만들었다 ("확인 필요"라고 코드에 남겨 둠). 이후 실제로 `curl`로 같은 엔드포인트를 불러보니: (1) 요청이 403으로 실패했고 — 원인은 `.env`의 인코딩된 인증키를 httpx가 쿼리 파라미터로 보내며 한 번 더 인코딩(이중 인코딩)한 것이었다. (2) 403을 우회해 정상 응답을 받아 보니, 첨부파일 URL·파일명 필드명(`ntceSpecDocUrl{n}`/`ntceSpecFileNm{n}` 짝, `specDocUrl{n}` 아님)과 분류 필드(`infoBizYn`, `pubPrcrmntLrgClsfcNm` 등)가 처음 추정한 것과 달랐다. (3) 저장 파일명을 URL에서 뽑는 로직도, 실제로는 첨부 URL이 전부 `downloadFile.do`라 파일 구분이 안 되는 걸 그제서야 알았다.

**원인**: 응답 구조를 추측으로 만들고, 그 추측에 맞춰 테스트 fixture까지 지어내면 테스트가 통과해도 아무것도 검증하지 못한다 — fixture 자체가 잘못된 가정을 그대로 반영하고 있기 때문이다. "테스트가 통과한다"와 "실제 API와 맞는다"는 완전히 다른 질문이었다.

**배운 것**: 외부 API를 연동할 때는 문서나 관행으로 좁힌 추정치를 "확인 필요"라고 표시해 두는 것만으로는 부족하고, 가능한 한 빨리 실제 호출(curl 등 가장 가벼운 도구로) 한 번을 해봐야 한다. 이번에는 curl 한 번으로 인증 문제(이중 인코딩)와 파싱 문제(필드명·파일명 매핑)를 동시에 찾았다 — 둘 다 단위 테스트만으로는 절대 못 잡는 종류의 문제였다. 실제 응답을 받은 뒤에는 fixture도 실제 구조로 다시 만들고, 실제로 걸러야 하는 반례("의상 제작 및 운영 용역" 같은 비SW 공고)를 지어낸 예시가 아니라 실제 응답에서 가져와 테스트에 넣었다.

## 2026-09-15 — 멱등성을 "같은 문서 중복 방지"로만 구현했더니 실행할 때마다 수집 대상이 늘었다

**무슨 일**: 이슈 #10을 실제로 두 번 연속 실행해 봤다. 1회차 "API 수집: 5건 신규", 2회차 "API 수집: 3건 신규"가 로그에 찍혔고, `data/raw/api/`의 파일이 5건에서 8건으로 늘었다. `collect.py` docstring에 "두 번 실행해도 파일 수가 늘지 않는다"고 적어 놨었는데, 이게 거짓으로 드러났다.

**원인**: `collect_from_api`의 `limit`을 "이번 실행에서 새로 받을 건수"로 구현했다. `doc_id` 기준 중복 방지(이미 아는 문서는 다시 저장하지 않음)는 정확히 지켰지만, 그건 "같은 문서를 두 번 저장하지 않는다"는 것만 보장할 뿐 "총 보유 건수가 어떤 목표치를 넘지 않는다"는 것과는 다른 성질이었다. 매 실행마다 아직 못 받은 **새로운(중복 아닌)** 후보를 `limit`건까지 찾아 계속 추가하니, 실행할수록 보유 건수가 무한히 늘어날 수 있는 구조였다.

**배운 것**: "멱등적이다"라고 말하기 전에 반드시 "무엇에 대해 멱등인지"를 먼저 정의해야 한다. 이번 경우 (1) 같은 문서를 중복 저장하지 않는다와 (2) 실행 횟수와 무관하게 보유 건수가 목표치를 넘지 않는다는 겉보기엔 비슷하지만 독립된 성질이고, (1)을 만족한다고 (2)가 저절로 따라오지 않는다. 고친 뒤에는 `limit`의 의미를 "이번 실행의 신규 건수"가 아니라 "manifest에 보유할 목표 총량"으로 바꾸고, 이미 목표치를 채웠으면 API를 아예 호출하지 않게 했다. `docs/data-design.md` 0절과 `collect.py` 모듈 docstring에도 두 성질을 명시적으로 구분해 적었다 — gitleaks rev, mypy 스코프, permission 문자열 매칭에 이어, "검증 장치가 의도한 범위만 보고 그 바깥은 못 본다"는 같은 패턴의 네 번째 사례다.

## 2026-09-16 — "pyhwp는 표 미지원"이라던 기각 근거가 실측과 달랐다

**무슨 일**: `docs/tech-stack.md` 8절은 애초에 "pyhwp는 2020년 이후 업데이트 없음·표 미지원·Python 3.9+ 호환 문제 → 비추천"이라 적고 LibreOffice headless + H2Orestart(이슈 #12)를 채택해 뒀다. 이슈 #11 사전 조사에서 실제로 `hwp5html --html`로 HWP 샘플을 변환해 보니, 요구사항 정의표 37개가 `<table>` 구조로 전부 멀쩡하게 나왔다.

**원인**: "표 미지원"이라는 판단은 pyhwp 패키지 자체가 아니라, pyhwp가 제공하는 여러 서브커맨드 중 텍스트만 뽑는 `hwp5txt`를 가리킨 것으로 보인다. `hwp5html`은 별도 서브커맨드고 표를 `<table>`로 보존한다 — 같은 패키지 안의 다른 도구를 하나로 뭉뚱그려 기각한 것.

**배운 것**: 라이브러리를 기각할 때 "이 라이브러리는 X를 못한다"는 근거는 그 라이브러리가 제공하는 여러 진입점(서브커맨드·모듈) 중 정확히 어느 것을 시험했는지까지 남겨야 한다. 그러지 않으면 나중에 실제로 확인하기 전까지는 그 판단이 맞는지 틀리는지 알 길이 없다. `docs/tech-stack.md` 8절을 "hwp5txt는 표를 버리지만 hwp5html은 표를 `<table>`로 보존한다(실측)"로 정정했다. "관리 중단" 리스크(2020년 이후 업데이트 없음)는 여전히 유효해 남겨 뒀고, 이슈 #12는 닫지 않고 pyhwp가 실패할 경우의 M2 백업 계획으로 남겼다.

## 2026-09-16 — 요구사항 접두어를 11개로 좁힌 정규식이 SIR을 놓쳐 71을 68로 셌다

**무슨 일**: 이슈 #11 사전 조사에서 천안시 PDF의 요구사항 코드를 셀 때, 미리 정한 11개 접두어(ECR·SFR·PER·INR·DAR·TER·SER·QUR·COR·PMR·PSR) 기준으로는 68개가 나왔다. 그런데 문서 22쪽 분류 요약표는 스스로 "합 계 71"이라고 밝히고 있었다 — 3개가 비었다.

**원인**: 이 문서는 인터페이스 요구사항에 흔히 쓰는 `INR`이 아니라 `SIR`을 썼다(`SIR-001`~`SIR-003`). 애초에 "실제 샘플로 반드시 확인"이라고 `docs/data-design.md`에 적어 두긴 했지만, 정규식을 짤 때 그 11개를 화이트리스트로 고정해 버려서 `SIR`이 통째로 안 잡혔다.

**배운 것**: 문서 자체가 총계("합 계 71")를 밝히고 있으면, 그 숫자와 파싱 결과를 항상 대조하는 게 접두어 목록이 틀렸다는 걸 잡아내는 가장 직접적인 방법이었다. 이슈 #11 구현에서는 접두어를 화이트리스트로 고정하지 않고 `^[A-Z]{3}-\d{3}$` 셀 전체 일치로만 코드를 판정하도록 바꿨고, `declared_total`과 파싱 개수가 다르면 `validation_warnings`에 남기는 검증을 코드에 넣었다(`docs/data-design.md` 3절).

## 2026-09-16 — 라벨 오타 "요구사항 교유번호"는 라벨 문구 매칭으로 조용히 누락된다

**무슨 일**: 이슈 #11 사전 조사에서 연구행정 데이터 기반 AI 플랫폼 구축 HWP 문서의 `SER-004`·`SER-005` 정의표를 라벨("요구사항 고유번호") 기준으로 찾았더니 2건이 빠졌다. 표를 직접 열어 보니 그 두 표만 라벨이 "요구사항 **교유**번호"(오타)로 돼 있었다.

**원인**: 정의표 판별 기준을 "라벨 문구가 '요구사항 고유번호'와 정확히 같은가"로 짰다. 문서 자체에 실수로 들어간 오탈자 하나가 그 표 전체를 판별 로직에서 빠뜨렸다 — 코드(`SER-004`)는 셀에 멀쩡히 있는데도 라벨 문구만 보다가 놓친 것.

**배운 것**: 사람이 손으로 쓴 문서는 라벨 문구 자체가 항상 일관되지 않을 수 있다. 이슈 #11 구현에서는 라벨 문구로 정의표를 판별하지 않고 "표 안에 요구사항 코드가 정확히 1개 있는가"라는 구조적 신호로 바꿨다 — 오타 여부와 무관하게 코드 셀 자체는 항상 정확했기 때문이다. 라벨은 "교유번호"를 별칭 사전에 명시적으로 추가해(`common.py` `LABEL_ALIASES`) 표준 필드로는 정상 매핑되게 하면서도, 원문 라벨은 `raw_fields`에 오타 그대로 보존했다.

## 2026-09-20 — 이슈 #47: 12자리 규격 vs 8자리 코드, 응답 구조 2종, 실험 전제 재점검

**12자리 규격과 8자리 코드**: 참고문서 규격(12자리)과 코드(8자리)가 달랐고, 수집이 성공하고 있었기 때문에 아무도 몰랐다. 서버가 부족한 HHMM을 0000으로 채워 종료일 당일 공고를 통째로 누락시켰다(실측 A=2915/B=2925/C=2915).

**응답 구조 2종**: 성공 응답과 에러 응답의 최상위 키가 달랐다(`response` / `nkoneps.com.response.ResponseError`). 코드가 한 쪽만 알아서 에러가 `None`으로 사라졌다. 알려진 구조를 하나 더 아는 것으로는 부족해서, 어떤 구조도 아닐 때 payload를 예외에 담는 경로를 넣었다.

**실험 전제 재점검**: 실측 전에 "어떤 값이 나오면 무엇으로 결론 낼지"를 먼저 정했다. 다만 그 기준 자체에 검증 안 된 전제(8자리=0000)가 섞여 있었고, 조작한 변수가 무엇인지 다시 따져서 실험을 한 번 더 했다.

## 2026-09-21 — 수집 필터 통과 원인은 infoBizYn이 아니라 SW_TITLE_KEYWORDS

**무슨 일**: 재즈 페스티벌 공고(R26BK01684655)가 수집 필터를 통과한 원인을 규명했다. `notice_title = "2026 송도 트라이보울 재즈 페스티벌 무대 시스템 설치 및 운영 용역"`이었고, `시스템`이 `SW_TITLE_KEYWORDS`("구축","고도화","시스템","정보화")에 걸려 통과했다.

**원인**: `is_sw_related`는 조기 반환(① infoBizYn=Y → ② 분류명 → ③ 공고명) 구조다. ③까지 내려왔다는 것은 ①②가 모두 False였다는 뜻이다 — infoBizYn은 Y가 아니었고 분류명에도 SW 키워드가 없었다. ①②는 이 공고를 걸러냈고, ③이 통과시켰다. (참고문서 확인: infoBizYn = 정보화사업여부(Y/N), 항목크기 1, 항목구분 0)

**배운 것**:
- 이슈 #47의 제목("infoBizYn 필터 검증")이 원인을 잘못 지목하고 있었다. 증상(비IT 공고가 통과)만 보고 가장 의심스러운 필드를 이슈 제목에 적어 9일간 그대로 뒀다. 조기 반환 순서를 따라가면 그 필드는 조건에서 이미 탈락한 상태였다.
- docstring이 ③을 "보조 기준"이라고 규정하는데, API 수집 9건의 제목을 보면 다수가 `시스템` 하나로 통과했다. 설계 의도와 실제 동작이 어긋나 있고, 어느 조건이 통과시켰는지 manifest에 남지 않아 사후 확인이 불가능하다.
- 기존 테스트(`test_ingest_nara_client.py:122`)는 infoBizYn=Y와 SW 분류가 동시에 참인 표본을 쓴다. 조기 반환 구조에서 이 표본은 어느 조건이 통과시켰는지 구별하지 못한다.

## 2026-09-22 — 이슈 #50: 수집이 1페이지만 받고 있었다

**무슨 일**: API는 페이지 단위로 응답하는데, 수집 코드가 `page_no`를 넘기지 않아 1페이지만 받고 있었다. 2026-07-01~07-31 `totalCount` 14282건 (#50 실측). 에러가 나지 않았고, 파일도 쌓였고, 테스트도 통과해서 몇 주 동안 몰랐다.

**원인**: 응답에 총량(`totalCount`)이 들어 있었지만, 받은 건수와 대조하는 코드가 없었다.

**배운 것**: "돌아간다"와 "다 받았다"는 다르다. 응답에 총량이 들어 있으면 받은 양과 대조해야 한다. #50에서 `search_all_service_bids`가 `totalCount`까지 모든 페이지를 받도록 하고, 구간별 `total_count`·응답 건수를 `data/raw/collect_runs.jsonl`에 남겨 `response_count < total_count`로 누락을 확인할 수 있게 했다.

두 수치는 구간이 다르다. 5배 차이의 원인은 확인되지 않았다 — 계절 요인인지, PR #48 당시 페이지네이션이 없어 total_count가 아닌 다른 값을 본 것인지 미확정.

## 2026-09-22 — 이슈 #50: 조회 기준 날짜가 UTC였다

**무슨 일**: 한국 공공 API를 부르면서 조회 기준 날짜를 `datetime.now(UTC).date()`로 구했다. KST 00:00~09:00에 실행하면 종료일이 전날이 되어 당일 공고가 빠진다.

**원인**: PR #48에서 고친 "종료일 자릿수" 버그(종료일 당일 공고 누락)와 같은 종류의 버그가 시간대 쪽에 남아 있었다.

**배운 것**: 한 종류의 버그를 고쳤다고 그 종류가 끝난 것이 아니다. #50에서 기준 날짜를 KST(`+09:00`)로 고정했다(`collect.py` `today_kst`). 단, **나라장터 조회 시각이 KST 기준이라는 것은 아직 확인되지 않은 전제다** — 참고문서로 확인하지 못했고, `docs/data-design.md` 1절에도 가정으로 적어 두었다.

## 2026-09-22 — 이슈 #52: 파싱 결과가 어디에도 저장되지 않았다

**무슨 일**: "요구사항 문서 2건"이라는 수치를 프로젝트 문서가 계속 물려받고 있었는데, 그 값의 출처가 되는 파일이 없었다. #52에서 파싱 결과를 `data/parsed/<doc_id>.json`에 저장하도록 만들고 실제로 세어 보니 `has_requirements=true`는 11건이었다.

**원인**: 파서는 결과를 반환만 하고 파일로 남기지 않았다. 숫자는 한 번 확인된 뒤 문서에서 문서로 옮겨지기만 했다.

**배운 것**: 판정 기준으로 쓰는 숫자는 파일로 남아 있어야 한다. 파일이 없으면 그 숫자가 지금도 맞는지 다시 셀 방법이 없다.

## 2026-09-22 — 이슈 #52: 테스트를 통과한 첫 구현이 실제로는 쓸모가 없었다

**무슨 일**: #52의 첫 구현에서 요약 로그가 형식·상태별 건수만 셌다. 다시 실행하면 전부 "건너뜀"으로 잡혀, 완료 기준(`has_requirements=true` 건수)을 그 출력으로 판정할 수 없었다. 단위 테스트는 통과했고, reviewer 서브에이전트가 잡았다.

**원인**: 완료 기준이 "이 명령의 출력으로 판정한다"였는데, 그 출력을 실제로 만들어 보지 않고 테스트 통과로 완료를 판단했다.

**배운 것**: 완료 기준이 "이 명령의 출력으로 판정한다"이면, 그 출력을 실제로 만들어 봐야 한다. 고친 뒤에는 요약 로그가 이번 실행 결과와 별도로 `data/parsed/` 전체의 `has_requirements=true` 건수를 출력한다(`parse.py` `count_has_requirements`).

## 2026-09-22 — (용어) "조용히" 같은 부사를 쓰지 않는다

**무슨 일**: 대화에서 쓰인 "조용히"(silently)라는 말이 docstring과 PR 본문까지 옮겨갔다.

**원인**: "조용히"는 무슨 일이 일어나는지 말하지 않는다 — 에러가 안 난다는 것인지, 기록이 안 남는다는 것인지, 값이 버려진다는 것인지 읽는 사람이 추측해야 한다.

**배운 것**: 무슨 일이 일어나는지 그대로 쓴다 — "에러 없이 일부만 받고 끝난다", "실패가 기록에 남지 않는다". CLAUDE.md 용어 규칙에 추가하고, 소스·테스트·설계 문서의 기존 "조용히"를 바꿨다. 이 학습 로그의 예전 기록(2026-09-16 "라벨 오타 … 조용히 누락된다" 항목 제목)에는 이 표현이 그대로 남아 있다 — 과거 기록을 새 규칙에 맞춰 고치면 그 용어를 썼다는 증거가 사라지므로 고치지 않았다.
