**구조 판정 (대상 1)**
- 요구사항 1개 = **표 1개** (하나의 `<table>` 안에 행 6개가 고정 라벨로 반복)
- 코드는 라벨 "요구사항 고유번호" 옆(같은 행의 두 번째 `<td>`) 셀에 있다 — 첫 열이 아니다
- 라벨 목록(실제 문구 그대로): `요구사항 분류` / `요구사항 고유번호` / `요구사항 명칭` / `요구사항 상세설명`(그룹 라벨) → `정의` / `세부내용` / `산출정보`. "관련 요구사항" 라벨은 이 문서에는 없다
- rowspan/colspan 사용함: 라벨 셀 대부분 `colspan="2"`(라벨을 두 셀로 합쳐 표시), "요구사항 상세설명" 라벨은 `rowspan="2"`로 정의·세부내용 두 행을 묶음
- **실측 함정**: `SER-004`, `SER-005` 두 표는 라벨이 `요구사항 고유번호`가 아니라 **`요구사항 교유번호`(오타)** 로 되어 있다. 문구 그대로 매칭하면 이 2건을 놓친다 — "코드 1개 + 행 2개 이상"이라는 구조 기준으로 바꾸고 나서야 37개 전부 잡혔다

**표 밖 등장 / 고유 코드 개수 (대상 1)**
- 요구사항 목록(요약)표가 **따로 1개** 있다 — 상세 요구사항표들보다 앞에 위치, 헤더: `요구사항 구분 | 고유번호(ID) | 요구사항 명 | 요구사항 수`. 37개 코드 전부 이 표 안에 1회씩 등장
- 그 외에는 코드가 표 밖(목차·본문)에 나오지 않았다 — 37개 코드 전부 정확히 **2회**(요약표 1회 + 상세표 1회)만 등장. 즉 이전 조사에서 나온 "37개"는 이 2중 집계와 무관하게 **고유 코드 개수 자체가 37개**였다(요약표와 상세표 둘 다 세면 74회가 되지만, 그건 이번에 처음부터 "고유 코드 수"로 집계했으므로 중복 문제는 아니었다)
- 느슨한 스캔(`[A-Z]{2,6}-\d{2,4}`, 주어진 11개 코드로 한정하지 않음)에서 `KO-10`이 추가로 1회 걸렸다 — 표준 인용구 `"KICS.KO-10.0307"`(모바일 웹 콘텐츠 저작 지침 번호)이지 요구사항 코드가 아니다. 2회가 아니라 1회만 등장해서 구분 가능했다
- **고유 코드 개수: 37개** (주어진 11개 코드 기준, 중복 제거 후)

### 대상 2 (PDF) — 첫 3개 요구사항 원본 셀

PyMuPDF `find_tables()`로 **표 구조가 그대로 잡힌다** (텍스트로만 나오지 않는다). 129페이지 중
25~86페이지 사이에서 정의표 68개가 발견됨(표 1개 = 요구사항 1개). 짧은 요구사항은 한 페이지에
여러 개가 들어가기도 한다 — 예: 67·70·78페이지는 각각 3개, 42·53·56~58·60·61·69·72~75·80~83·86페이지는
각각 2개씩 들어 있다(20개 페이지가 2개 이상).

(페이지 경계에서 열 인식이 흔들려 3번째 열이 통째로 안 잡힘).

**구조 판정 (대상 2)**
- 요구사항 1개 = **원칙적으로 표 1개** (7행 × 3열, `None`은 pymupdf가 병합 셀을 나타내는 방식 — 실제 PDF에는 rowspan/colspan 속성이 없고, 시각적 셀 병합을 pymupdf가 추론한 결과다). 다만 세부내용이 길어 페이지를 넘기면 표가 여러 개 조각으로 쪼개진다(아래 "표 밖 등장" 참고)
- 코드는 라벨 `요구사항\n고유번호` 행의 **3번째 열(마지막 열)**에 있다 — 1열은 라벨, 2열은 이 행에서는 `None`(병합)
- 라벨 목록(원문 그대로, 개행 포함): `요구사항 분류` / `요구사항\n고유번호` / `요구사항 명칭` / `요구\n사항\n세부\n내용`(그룹 라벨) → `정의` / `세부\n내용` / `산출정보` / `관련요구사항`
- "관련요구사항" 라벨이 있다는 점이 대상 1과 다르다(대상 1엔 없음). 확인된 값은 전부 빈 문자열이었다

**표 밖 등장 / 고유 코드 개수 (대상 2)**
- 요구사항 목록표가 **페이지 경계로 쪼개져 2개의 표 객체**로 잡힌다 — 23페이지(8행, 코드 33개)와 24페이지(6행)에 각각 헤더 행(`연번 | 구 분 | 고유번호 | 요구사항 명칭`)이 반복 출력된다. pymupdf가 페이지 단위로 표를 인식하기 때문에, 원래 하나였을 목록표가 페이지를 넘어가면 별개의 표로 분리된다
- **목록표뿐 아니라 개별 요구사항 정의표도 페이지 경계에서 쪼개진다.** 68개 정의표 시작 조각의 행 수를 세어 보면 7행(완결) 53개, 5행(산출정보·관련요구사항이 다음 페이지로 넘어감) 14개, 2행(고유번호까지만 나오고 나머지는 다음 페이지) 1개(`QUR-003`, 67페이지) — **15/68(약 22%)가 최소 한 번은 페이지 경계로 잘려 있다.** 이어지는 조각은 라벨 열이 비어 있는(`['', '', '...']`) 표로 잡혀, 이번 정의표 판별 기준("코드 1개 포함")에는 걸리지 않는다(코드가 없으니 당연히 안 걸림) — 즉 68이라는 개수는 "표 시작 조각의 개수"이지 "완전한 요구사항 텍스트가 1개 표에 들어 있는 개수"가 아니다
  - **정정(#11 구현, PR #46)**: 위 "15"는 행 수(<7)만 보고 추정한 근사치였다. 실제로 페이지를 이어붙이는 로직을 구현해 측정하니 **SIR 포함 71개 기준 15개**가 페이지 경계로 잘려 있었다(우연히 같은 숫자, 기준 코드 집합은 다름). 처음 구현했을 때는 11개로 나왔다. 그 5건(`ECR-005`·`ECR-007`·`SER-006`·`SFR-003`·`SFR-005`)을 "이어지는 조각의 산출정보·관련요구사항 값이 둘 다 비어 있다"고 처음 설명했는데, **이 설명은 사용자가 PDF 원본과 직접 대조해 틀렸음이 드러났다** — 값은 실제로 있었고(예: `ECR-005`의 산출정보 = "납품확인서, 설치계획서, 설치결과서, 기술지원확약서"), `find_tables()`가 그 값 열 자체를 bbox 밖으로 놓쳐 표 밖 자유 텍스트(문단)로 떨어뜨린 것이었다. 여기에 더해 같은 원인으로 `QUR-003`(6번째 사례)의 name/definition/output도 비어 있었다 — 표준 필드 "존재"만 확인하는 검사로는 못 잡고, 값이 채워졌는지까지 봐야 드러났다. `pdf_parser.py`의 `absorb_trailing_paragraphs`로 표 밖에 떨어진 문단을 되찾도록 고쳤다(`tests/integration/test_parse_real_files.py`).
- 주어진 11개 코드 기준으로 68개 코드 전부 정확히 **2회**(목록표 1회 + 상세표 시작 조각 1회) 등장 — 표 밖(본문·목차)에서 추가로 나오는 코드는 없었다
- **주어진 11개 코드 목록에 없는 접두어가 실제로 쓰였다**: 이 문서는 인터페이스 요구사항에 `INR`이 아니라 **`SIR`**을 쓴다(`SIR-001`~`SIR-003`, 각 2회). `INR`은 이 문서에 0건이다
- 느슨한 스캔에서 `SUS-316`이 1회 걸렸는데, 이는 요구사항 코드가 아니라 스테인리스강 재질 규격(`SUS-316L`, 함체 소재)이다 — 1회만 등장해서 구분 가능했다
- 문서 서두 "5. 요구사항 목록표" 앞 요약 문단에 "합 계 71"이라는 문구가 있다 — `SIR` 3개를 포함하면 실제 고유 코드 71개(주어진 11개 코드만 세면 68개)로 문서가 스스로 밝힌 총계와 일치한다
- **고유 코드 개수: 68개**(주어진 11개 코드 기준) / **71개**(문서에 실제 쓰인 `SIR` 포함, 문서 자체 "합 계" 문구와 일치)

### 대상 1 vs 대상 2 — 구조 차이

| 항목 | 대상 1 (HWP→HTML) | 대상 2 (PDF) |
|---|---|---|
| 요구사항 1개 단위 | `<table>` 1개 | `find_tables()` 표 1개 |
| 표 행 수 | 6행 고정 | 7행 고정 |
| 코드 위치 | "요구사항 고유번호" 행의 2번째 `<td>` | "요구사항 고유번호" 행의 3번째 열(마지막) |
| "관련 요구사항" 라벨 | 없음 | 있음(첫 3건은 빈 값) |
| 병합 표현 | HTML `rowspan`/`colspan` 속성 | pymupdf가 `None`으로 표시(원본엔 속성 없음) |
| 라벨 오탈자 | `SER-004`/`SER-005`에서 "고유번호"→"교유번호" 오타 발견 | 발견되지 않음(첫 3건 기준) |

### 제안

- 정의표 판별은 라벨 문구 정확 매칭("요구사항 고유번호")에 의존하면 안 된다 — 대상 1의 실제 오타(`교유번호`)에서 바로 깨진다. "표 안에 요구사항 코드가 정확히 1개 있고 행이 여러 개"처럼 코드 패턴 중심으로 판별하는 편이 오타·표기 흔들림에 더 강하다
- 요구사항 코드 정규식을 주어진 11개 접두어로 고정하면 대상 2의 `SIR`처럼 실제 문서가 쓰는 접두어를 놓칠 수 있다 — 접두어를 화이트리스트로 고정하기보다, "표의 '요구사항 고유번호' 행 값" 같은 구조적 위치에서 뽑아내고 접두어는 사후에 집계하는 방식이 안전해 보인다
- 코드 비슷한 문자열(`KO-10`, `SUS-316`)이 자유 텍스트에 섞여 있어, 표 밖 본문을 정규식으로 훑는 방식은 오탐 위험이 있다 — 두 문서 다 실제 요구사항 코드는 항상 표 안에서만 나왔으므로, 표 구조에서 뽑는 접근이 표 밖 프리텍스트 스캔보다 안전해 보인다
- PDF는 페이지 경계에서 표가 쪼개진다 — 목록표뿐 아니라 **개별 요구사항 정의표도 22%가 조각난다**(대상 2 실측). 페이지별로 `find_tables()` 결과를 독립적으로 쓰면 안 되고, 앞 페이지 표의 마지막 줄이 다음 페이지 표의 라벨 없는 이어짐인지(라벨 열이 빈 문자열인 행) 판단해 같은 요구사항으로 이어붙이는 처리가 필요해 보인다
- 두 문서의 라벨 구성이 달라(대상 2에만 "관련요구사항") 스키마를 설계할 때 이 필드를 옵셔널로 두는 편이 나아 보인다
