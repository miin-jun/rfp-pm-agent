## 2. 세 회사가 원하는 공통 6가지

`docs/architecture.md` 2절의 "구성요소 ↔ 공고 매핑" 표에서, **세 회사 모두**가 어떤 형태로든 요구하는 항목만 뽑으면 6가지다 (회사마다 부르는 이름은 다름):

| 공통 요구 | 컴앤휴먼 | 뉴데이소프트 | 식신 |
|---|---|---|---|
| 1. 데이터 수집 파이프라인 | 문서 수집·전처리 | 데이터 수집 | Databricks·PySpark·Airflow |
| 2. 검색 엔진 (BM25 + 벡터) | Hybrid·ES/OpenSearch·pgvector | ES 환경 | Vector Search |
| 3. 근거 기반 답변 (Grounded RAG) | Grounded RAG | RAG | RAG |
| 4. 에이전트 | Project AI Assistant | 업무 자동화 Agent | AI Agent |
| 5. 평가·관측 | LLMOps | Agent 평가 | 운영·개선 |
| 6. 배포 | Docker·Cloud | Linux | AWS EC2·S3 |

이 6가지가 MVP(Phase 1)의 핵심 뼈대다. 권한 필터(RBAC)·MCP 서버·개발 하네스는 셋 중 한두 회사만 명시적으로 요구하지만, 이 프로젝트에서는 어차피 다 만든다 (하네스는 이미 Phase 0에서, MCP는 Phase 1에서).

## 3. 무엇을 만드나

### 완성 시 동작 예시 한 장면

사용자(개발자 역할)가 묻는다: **"이번 주 지연된 업무랑 관련된 요구사항 문서 알려줘"**

1. 에이전트가 질문을 해석해 두 가지가 필요하다고 판단
2. `get_delayed_tasks(week=이번주)` 실행 → PostgreSQL에서 지연 업무 목록 (예: "데이터 이관 설계")
3. `search_documents("데이터 이관 설계 요구사항")` 실행 → BM25(키워드) + 벡터(의미) 검색을 RRF로 합치고 리랭커로 재정렬
4. 두 결과를 결합해 답변 생성: 업무별 지연 일수 + 관련 요구사항 원문 + **`[제안요청서 p.23, DAT-003]`** 같은 출처
5. 근거가 없는 질문에는 "문서에서 찾을 수 없음"이라고 답함 (환각 억제)

(자세한 흐름은 `docs/architecture.md` 3절, 정확한 툴 이름은 `docs/github-setup.md` 이슈 #21 참고)

### 데이터 출처 — 실제 RFP vs 합성 PMS를 구분할 것

이 프로젝트는 **성격이 다른 데이터 두 종류**를 섞어 쓴다. 헷갈리기 쉬우니 명확히 구분한다.

| | 실제 데이터 | 합성 데이터 |
|---|---|---|
| **무엇** | RFP 원문 (PDF·HWPX·HWP) | PMS(WBS·일정·Risk·Issue·산출물) |
| **출처** | 나라장터 API 자동 수집 + 착수 초기 수동 반입 5건 | RFP 요구사항을 근거로 코드 + LLM이 생성 |
| **진짜인가** | 그렇다 — 실제 공공 입찰 공고 문서 | 아니다 — 실제 프로젝트가 아니라 시연·평가용으로 만든 것 |
| **정답을 어떻게 아는가** | 원문 자체가 근거(그래서 출처를 원문 그대로 인용) | "정답을 알고 만든다" 원칙 — 코드가 지연·Risk를 의도적으로 심어서 평가 정답이 생성 과정에서 자동으로 나옴 (`docs/data-design.md` 7절) |
| **권한 등급** | `public` (RFP 원문은 전체 역할이 열람 가능) | `internal`/`confidential` 합성 문서를 Phase 2에 추가해 RBAC 시연 |

즉, "지연된 업무"·"Risk"는 전부 가짜(합성)이고, 그 업무·Risk와 연결된 "요구사항 원문"은 진짜(실제 RFP)다. 답변에 달리는 출처 중 PMS 관련 수치는 합성 데이터에서, 요구사항 인용은 실제 RFP에서 나온다는 것을 항상 구분해서 설명해야 한다 (특히 이력서·면접에서 "실제 데이터로 뭘 했는지" 질문에 정확히 답하기 위해).

## 4. 완성되면 이력서에 쓸 수 있는 것

**이미 확보한 것 (Phase 0, 2026-09-14 기준 완료)**
- Claude Code 하네스(가이드·권한 규칙·훅·pre-commit·CI·리뷰 서브에이전트)를 설계하고, 실제로 3건의 방어 실패 사례를 실측으로 찾아 문서화함: gitleaks 구버전이 가짜 키를 못 잡던 문제, 훅과 pre-commit의 mypy 검사 범위가 달라 같은 오류를 한쪽만 잡던 문제, `.env` deny 규칙이 도구 호출 경로만 막고 스크립트 직접 오픈은 못 막는 것 (`docs/learning-log.md`)
- GitHub Issues 기반 개발 프로세스 구축: 이슈 = 작업 지시서, 브랜치 → PR(`Closes #N`) → squash 머지 → 이슈 자동 종료, CI가 로컬 훅과 독립적으로 검사함을 실측 검증
- "Elasticsearch 무료 티어는 RRF가 막혀 있어, 같은 계열이면서 Apache 2.0으로 RRF를 내장한 OpenSearch를 선택했다" 같은, 근거를 남긴 기술 선택 (`docs/tech-stack.md`)

**Phase 1·2를 마치면 추가될 것 (아직 미완성 — 🔜)**
- 🔜 공개 벤치마크로 임베딩·리랭커 후보를 좁히고, 자체 RFP 평가셋으로 Recall@10을 실측해 "1위와 1%p 이내면 가벼운 모델 선택"이라는 결정 규칙을 미리 정해 적용한 사례 (#16)
- 🔜 LangGraph 멀티스텝 에이전트 + Trajectory(과정) 평가 — 정답 여부뿐 아니라 툴 호출 순서까지 채점 (#22, #25)
- 🔜 권한(RBAC) 사전 필터 설계 — "권한 필터를 사후가 아니라 사전에 두는 이유"에 대한 근거 있는 답변, 권한 유출 자동 테스트 (Phase 2)
- 🔜 MCP 서버로 Claude Desktop 같은 다른 AI 도구에서 실제로 호출되는 데모 (#24)
- 🔜 Private LLM(RunPod vLLM) vs OpenAI API를 같은 평가 세트로 비교한 수치 (Phase 2, 컴앤휴먼 "On-Premise LLM" 우대 대응)
- 🔜 훅·CI가 잡아낸 오류 건수, PR의 CI 첫 통과율 같은 하네스 효과 수치 (`docs/harness.md` 12절, `.claude/logs/hook_events.jsonl` 누적 후 집계)
